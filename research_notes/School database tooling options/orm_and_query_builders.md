# ORMs and query builders for a Node.js/TypeScript service calling stored procedures in many third-party SQL Server databases (state as of 2026-11-10)

All version numbers and dates below were read from the npm registry JSON on 2026-11-10 unless stated otherwise. Verification legend used in the findings: **[raw]** = I read the raw page text or the published source file myself; **[summ]** = page read through a summarising fetch tool (wording may be slightly off, treat quotes as close paraphrase); **[snippet]** = search-result snippet only, not opened.

## 1. Current state of Microsoft SQL Server support in Prisma (incl. TypedSQL), Drizzle, Kysely, Knex, TypeORM, Sequelize, MikroORM

### Takeaway
Stable SQL Server support exists today in Prisma ORM 7, Kysely, Knex, TypeORM 1.x, Sequelize 6 and MikroORM 7; Drizzle has it only in the unreleased 1.0 line (release candidate), Sequelize 7 is still alpha, and the new Prisma ORM 8 (release candidate, and what `npm install prisma` now installs) does not support SQL Server at all. Prisma's TypedSQL feature does not cover SQL Server.

### Inferences
- TypedSQL is effectively unavailable for this project: the docs list only MySQL/PostgreSQL/SQLite and two "TypedSQL for SQL Server" requests have been open since 2024/2025. Even if it existed it types `.sql` query files, not stored-procedure calls with several result sets.
- Prisma is the riskiest choice for SQL Server right now: the vendor's current major (8 RC) drops SQL Server "until later", so a SQL Server user is pinned to the previous major with no published date for parity. This matches the project's earlier decision to remove Prisma 7.
- Drizzle for SQL Server means running a release candidate in a payments service; Sequelize v7 means running an alpha. Only Kysely, Knex, TypeORM 1.x, MikroORM 7 and Sequelize 6 offer SQL Server on a normal release line.
- Every candidate ultimately sits on `tedious` (directly, or through `mssql`), the same stack the service already uses. None adds a protocol capability the current driver lacks.

## 2. Stored procedures with typed inputs AND typed results, including MULTIPLE result sets

### Takeaway
None of the seven tools can call an existing SQL Server procedure with typed inputs, typed results and multiple result sets; six offer only a raw `EXEC` string escape hatch, and those either return only the first result set or merge all sets into one array. MikroORM 7.1+ is the only one with a real routine API, but it is experimental and explicitly does not surface multiple result sets on SQL Server. The plain `mssql` driver the project already uses is the only layer in the stack that exposes every result set, output parameters and the return value.

### Cited Findings
- Baseline, `mssql` README: `request.input(...)`, `request.output('output_parameter', sql.Int)`, `request.execute('procedure_name')`; the result exposes `result.recordsets.length` ("count of recordsets returned by the procedure"), `result.recordset` ("first recordset from result.recordsets"), `result.returnValue` ("procedure return value") and output parameters; Table-Valued Parameters are supported for procedures. [raw] — [mssql README via registry](https://registry.npmjs.org/mssql)
- Prisma 7 (`@prisma/adapter-mssql` 7.10.1): `queryRaw` runs `req.query(query.sql)` with positional inputs `P1..Pn` and then destructures only `recordset` (`const { recordset, columns: columnsList } = await this.performIO(query)`); additional recordsets are discarded. It never calls `request.execute`. [raw] — [unpkg @prisma/adapter-mssql 7.10.1](https://unpkg.com/@prisma/adapter-mssql@7.10.1/dist/index.js)
- Prisma feature request "Execute stored procedures and work with return value and output parameters" has been OPEN since 2022-12-13. [raw, title/state] — [prisma/orm #16776](https://github.com/prisma/orm/issues/16776)
- Drizzle 1.0.0-rc.5 (`node-mssql/session.js`): parameters are bound as `par0..parN` with inferred types (only `Date` is mapped explicitly, to `DateTime2(7)`); the executor returns `request.query(query.sql).then((res) => res.recordset)` (first recordset only) except in an internal `"raw"` mode, which returns the untouched node-mssql result. No `request.execute` call. [raw] — [unpkg drizzle-orm 1.0.0-rc.5 node-mssql/session.js](https://unpkg.com/drizzle-orm@1.0.0-rc.5/node-mssql/session.js)
- Kysely 0.29.8 (`mssql-driver.js`): uses `connection.execSql(request)`; every tedious `'row'` event is pushed into one `#rows` array that is returned as `rows`; there is no `callProcedure` and no handling of result-set boundaries. [raw] — [unpkg kysely 0.29.8 mssql-driver.js](https://unpkg.com/kysely@0.29.8/dist/dialect/mssql/mssql-driver.js)
- Knex 3.3.0 (`lib/dialects/mssql/index.js`): `connection.execSql(nextRequest)`; `request.on('row', (row) => { rows.push(row) })` into a single array; no `callProcedure` in the file. An issue titled "Multiple result sets" (opened 2017-09-12) is closed. [raw for source; title/state only for issue] — [unpkg knex 3.3.0 mssql dialect](https://unpkg.com/knex@3.3.0/lib/dialects/mssql/index.js), [knex #2222](https://github.com/knex/knex/issues/2222)
- TypeORM 1.1.2 (`SqlServerQueryRunner.js`): `const raw = await request.query(query)`; `result.records = raw.recordset`; `result.raw = raw.recordset` (first recordset only). Issues "Multiple Recordsets in stored procedure" (opened 2019-11-06) and "MSSQL EntityManager.query(`EXEC <SP>`, [param]) doesn't return all recordsets, only the first one" (opened 2025-07-08) are both OPEN; the fix PR "fix(sqlserver): queries returning multiple record sets" (opened 2025-07-21) is still OPEN and unmerged. [raw] — [unpkg typeorm 1.1.2 SqlServerQueryRunner.js](https://unpkg.com/typeorm@1.1.2/driver/sqlserver/SqlServerQueryRunner.js), [typeorm #5051](https://github.com/typeorm/typeorm/issues/5051), [typeorm #11566](https://github.com/typeorm/typeorm/issues/11566), [typeorm PR #11576](https://github.com/typeorm/typeorm/pull/11576)
- Sequelize 6.37.8 (`lib/dialects/mssql/query.js`): `connection.execSql(request)`; rows from `request.on("row", ...)` are pushed into one array; parameter SQL types are guessed from the JavaScript value (`getSQLTypeFromJsType`). Issue "Multiple result sets of stored procedure getting merged into one array" has been OPEN since 2017-10-24. [raw] — [unpkg sequelize 6.37.8 mssql query.js](https://unpkg.com/sequelize@6.37.8/lib/dialects/mssql/query.js), [sequelize #8525](https://github.com/sequelize/sequelize/issues/8525)
- MikroORM stored routines: "Stored-routine support landed in v7.1 and is considered experimental while we gather real-world feedback. The configuration types (RoutineConfig, RoutineParamConfig, RoutineReturns) and runtime behaviour may evolve in a patch release. Pin your MikroORM version if you rely on the exact API shape." (7.1.0 was published 2026-05-20.) [raw] — [MikroORM docs, Stored Routines](https://mikro-orm.io/docs/stored-routines)
- MikroORM: routines are declared (`name`, `type`, `params`, `returns`, `body`) and invoked with `em.callRoutine(routine, args)`; parameter TypeScript types are derived from the declared SQL types; OUT/INOUT parameters on SQL Server are bridged with a "T-SQL batch with DECLARE @v ...; SET @v = ?; EXEC proc ?, @v OUTPUT; SELECT @v". Declared routines are created/dropped/altered by the schema generator unless `schemaGenerator: { ignoreRoutines: true }` is set. [raw for the OUT-param quote; summ for the rest] — [MikroORM docs, Stored Routines](https://mikro-orm.io/docs/stored-routines)
- MikroORM on multiple result sets: "MSSQL: result sets emitted by a procedure are not surfaced through em.callRoutine — tedious flattens them through the kysely wrapper without per-set boundaries. Use em.getConnection().execute() for raw multi-recordset access." and "em.callRoutine returns Dictionary[][] only for MySQL/MariaDB, PostgreSQL, and Oracle. Entity-typed result-set hydration (mapping rows onto entity classes) is not yet supported". Static tuple typing of multiple sets is listed as a follow-up. [raw] — [MikroORM docs, Stored Routines](https://mikro-orm.io/docs/stored-routines)
- Community wrapper `@hunter-ashmore/kysely-mssql` advertises a `callStoredProcedure` helper "with typed parameters". [snippet, not inspected] — [pkgstats listing](https://www.pkgstats.com/pkg:@dev-hla/kysely-mssql)

Summary table (derived from the findings above):

| Tool | Procedure API | How the call is sent | Input types | Result types | Multiple result sets on SQL Server |
|---|---|---|---|---|---|
| `mssql` (current) | `request.execute(proc)` | RPC call | explicit `sql.*` types per `.input()` | hand-written TS types | all sets in `result.recordsets`, plus `output`, `returnValue` |
| Prisma 7 | none (raw `EXEC`) | `request.query` batch | inferred | none | first set only |
| Drizzle 1.0-rc | none (raw `EXEC`) | `request.query` batch | inferred | hand-written | first set only (non-raw modes) |
| Kysely 0.29 | none (raw `EXEC`) | tedious `execSql` | inferred | hand-written | all rows merged into one array |
| Knex 3.3 | none (raw `EXEC`) | tedious `execSql` | inferred | none | all rows merged into one array |
| TypeORM 1.1 | none (raw `EXEC`) | `request.query` batch | inferred or parameter object | none | first set only (open issue since 2019) |
| Sequelize 6 | none (raw `EXEC`) | tedious `execSql` | guessed from JS type | none | merged into one array (open issue since 2017) |
| MikroORM 7.1+ | `em.callRoutine` (experimental) | T-SQL batch | derived from declaration | scalar typed; rows are plain dictionaries | not surfaced; flattened |

### Inferences
- "Merged into one array" for Kysely and Knex is my reading of the source (a single `'row'` listener, no result-set boundary tracking); MikroORM's documentation independently states the same about "the kysely wrapper", and Sequelize's open issue title states it for Sequelize.
- Replacing `pool.request().input(...).execute('proc')` with any of these tools would be a functional downgrade for this service: it would lose explicit TDS parameter types (relevant for money/decimal amounts and VARCHAR vs NVARCHAR), output parameters, return values and separate result sets. To keep them, the code would have to reach around the ORM to the underlying `mssql` request, which is what the service already does.
- "Typed results" for a stored procedure are not produced by any of these tools; in all cases the developer writes the TypeScript row types by hand, exactly as with plain `mssql`.

### Gaps
- I did not test any of this against a live SQL Server; the multi-result-set conclusions rest on reading published source files and issue titles/states (issue bodies were not read).
- Drizzle: I did not confirm which mode `db.execute()` uses on SQL Server, so whether it can return the full node-mssql result (with `recordsets`) is unverified.
- Sequelize v7 alpha (`@sequelize/mssql`) source was not inspected; the finding is for v6.
- MikroORM does not explicitly document whether `em.getConnection().execute()` returns per-set boundaries on SQL Server; given the "kysely wrapper flattens" statement it probably does not, but this is unverified.
- `@types/mssql` generic typing of `execute<T>()` results was not inspected in this session.

## 3. Many databases with DIFFERENT schemas at runtime (one client/schema per tenant) and the documented costs

### Takeaway
All candidates model a database as a schema known at build time (generated client, contract, entity classes or a TypeScript interface), so heterogeneous school databases mean one schema artefact and one client plus pool per distinct ERP layout; none offers a runtime-discovered, per-tenant schema. I found little vendor documentation that quantifies the cost, and none that addresses hundreds of tenants with differing third-party schemas.

### Cited Findings
- Prisma (current guide, written for Prisma ORM 8): "You give each database its own data contract, its own `prisma.config.ts`, and its own Prisma ORM client"; described as "a good fit for multi-tenant apps or for keeping unrelated data in separate databases"; each command is run once per config (`--config`); cross-database relations cannot be declared; each client opens its own pool on first use ("The pools are shared across requests and close when the process exits"). [summ] — [Prisma docs, Multiple databases guide](https://www.prisma.io/docs/guides/multiple-databases)
- Prisma TypedSQL needs a live database connection at generate time, configured as a single connection string in `prisma.config.ts`. [summ] — [Prisma docs, TypedSQL](https://www.prisma.io/docs/orm/prisma-client/using-raw-sql/typedsql)
- Community guidance for Prisma with one database per tenant is to construct one client per database and keep a map/cache of clients; the same answer states Prisma has no first-class multi-tenancy support. [snippet; the answer is from an AI help bot on a community mirror, low reliability] — [Answer Overflow thread](https://www.answeroverflow.com/m/1441519031248228382)
- Drizzle can wrap an existing `mssql` pool per database (`drizzle({ client: pool })`); a separate guide exists for adopting an existing SQL Server database. [summ] — [Drizzle docs, Get started with MSSQL](https://orm.drizzle.team/docs/get-started/mssql-new), [Drizzle docs, MSSQL in existing project](https://orm.drizzle.team/docs/get-started/mssql-existing)
- `kysely-codegen` 0.20.0 (2026-02-16) generates Kysely types by introspecting a live database and lists `mssql` among its dialects (`postgres`/`mysql`/`sqlite`/`mssql`/...). Its README does not mention stored procedures. [raw] — [kysely-codegen README via registry](https://registry.npmjs.org/kysely-codegen)
- `@rmp135/sql-ts` 2.2.0 (2024-11-23): "Generate TypeScript types for tables and views in a SQL database." [raw] — [sql-ts README via registry](https://registry.npmjs.org/@rmp135%2Fsql-ts)
- A vendor blog on ERP integrations describes the same shape for SAP Business One: each tenant runs against a separate SQL Server database, each needs its own session, and per-tenant schema variation must be handled at the database level. [snippet, vendor marketing content, low reliability] — [Ampersand blog](https://www.withampersand.com/blog/multi-tenant-erp-integrations-for-ai-products)

### Inferences
- For this project the schema the API sees is NOT heterogeneous: every school exposes the same 4 procedures with the same parameters and result shapes. The heterogeneity is hidden inside the per-school procedure bodies. An ORM would re-expose that heterogeneity to the application: the app would need a typed model of each ERP's tables (hundreds of tables, differing per school) just to rebuild queries that the per-school procedures already encapsulate.
- Costs that follow directly from the documented model: (a) one introspection/codegen run per distinct ERP schema, against a live copy of that database; (b) one generated artefact per distinct schema committed or built in CI; (c) application branching to select the right client/model per school; (d) one pool per school database, which is the same as today with one `mssql` `ConnectionPool` per school, so pooling is neither better nor worse.
- With schemas that are "customised per school", the number of distinct schema artefacts can approach the number of schools, so codegen does not collapse the variation; it only records it in TypeScript.

### Gaps
- I could not open a Prisma 7 version of the multiple-databases guide (several v7 URLs returned 404). My recollection that v7 requires a separate schema file, a separate generator `output` directory and a separate `prisma generate --schema` run per database is unverified in this session.
- No documented figures found for: generated client size per schema, introspection time or failure modes on a multi-hundred-table third-party SQL Server schema, or memory cost of holding dozens to hundreds of ORM clients in one Node process.
- No official multi-tenant (database-per-tenant) guidance was located for Drizzle, Kysely, Knex, TypeORM, Sequelize or MikroORM in this session; their multi-database mechanics were not individually verified.
- I found no reliable practitioner write-up specifically about "database per tenant with heterogeneous third-party schemas" in the Node.js ecosystem; the results were generic multi-tenancy posts and vendor marketing.

## 4. Do ORMs/query builders require direct table permissions? Contrast with an EXECUTE-only login

### Takeaway
Yes: every candidate sends ad hoc SELECT/INSERT/UPDATE statements under the application login, so using their table features requires granting that login table permissions and gives up the EXECUTE-only perimeter. Microsoft documents that with ownership chaining a caller needs only EXECUTE on a procedure and can be denied all access to the underlying tables.

### Cited Findings
- Microsoft: "One method of creating multiple lines of defense around your database is to implement all data access using stored procedures or user-defined functions. You revoke or deny all permissions to underlying objects, such as tables, and grant EXECUTE permissions on stored procedures. This effectively creates a security perimeter around your data and database objects." [raw; archived .NET Framework article dated 2017-03-30] — [Microsoft Learn, Managing Permissions with Stored Procedures in SQL Server](https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server)
- Microsoft: "Stored procedures take advantage of ownership chaining to provide access to data so that users do not need to have explicit permission to access database objects. An ownership chain exists when objects that access each other sequentially are owned by the same user. ... If all objects in the chain of execution have the same owner, then SQL Server only checks the EXECUTE permission for the caller, not the caller's permissions on other objects. Therefore you need to grant only EXECUTE permissions on stored procedures; you can revoke or deny all permissions on the underlying tables." [raw] — [same article](https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server)
- Same article lists as benefits: "Ad hoc queries and data modifications can be disallowed", and "Client applications do not need to know anything about the underlying data structures. Stored procedure code can be changed without requiring changes in client applications as long as the changes do not affect parameter lists or returned data types." It also advises "Avoid dynamic SQL unless absolutely necessary." [raw] — [same article](https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server)
- Current SQL Server tutorial (applies to SQL Server 2017 and later, page updated 2026-10-19): a user with no table permissions gets "Msg 229 ... The SELECT permission was denied on the object 'PurchaseOrderHeader'" on a direct `SELECT`, yet after `GRANT EXECUTE ON OBJECT::Purchasing.usp_ShowWaitingItems TO TestEmployeeUser`, "Because the objects referenced by the stored procedure ... are owned by TestManagerUser by virtue of the Purchasing schema ownership, TestEmployeeUser can access the base tables through the stored procedure." [raw] — [Microsoft Learn, Tutorial: Ownership Chains and Context Switching](https://learn.microsoft.com/en-us/sql/relational-databases/tutorial-ownership-chains-and-context-switching)
- All candidates execute application-composed SQL batches under the connection's login: Prisma adapter `req.query(query.sql)`; Drizzle `request.query(query.sql)`; TypeORM `request.query(query)`; Kysely, Knex and Sequelize `connection.execSql(request)`. [raw] — [Prisma adapter](https://unpkg.com/@prisma/adapter-mssql@7.10.1/dist/index.js), [Drizzle](https://unpkg.com/drizzle-orm@1.0.0-rc.5/node-mssql/session.js), [TypeORM](https://unpkg.com/typeorm@1.1.2/driver/sqlserver/SqlServerQueryRunner.js), [Kysely](https://unpkg.com/kysely@0.29.8/dist/dialect/mssql/mssql-driver.js), [Knex](https://unpkg.com/knex@3.3.0/lib/dialects/mssql/index.js), [Sequelize](https://unpkg.com/sequelize@6.37.8/lib/dialects/mssql/query.js)
- Metadata discovery is also permission-bound: `sp_describe_first_result_set` "Requires permission to execute the @tsql argument." [raw] — [Microsoft Learn, sp_describe_first_result_set](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-describe-first-result-set-transact-sql)

### Inferences
- Because the tools send ad hoc DML, an EXECUTE-only login would receive error 229 on every model query. Adopting an ORM/query builder for table access therefore forces a choice: grant SELECT/INSERT/UPDATE on third-party ERP ledger and receipt tables to the internet-facing API's login, or keep the perimeter and use the ORM only as a wrapper for `EXEC` strings (where, per question 2, it is weaker than the current driver).
- With table grants, a SQL-injection bug or stolen credential could read or write any granted ERP table; with EXECUTE-only on 4 procedures, the reachable surface is exactly those 4 operations. This is the "security perimeter" Microsoft describes, and it is an argument for keeping the current design regardless of tooling.
- Ownership chaining only holds when the procedures and the ERP tables share an owner (typically both in `dbo`). If a school's ERP tables live in a schema with a different owner, the chain breaks and the procedure would need another mechanism. This is a property to check per school, independent of the ORM question.
- ORM introspection/codegen of the ERP schema would additionally need a login with metadata visibility on all ERP tables in each school database, at least at build or onboarding time.

### Gaps
- I did not fetch a current (non-archived) Microsoft page that states in one sentence that dynamic SQL inside a procedure and cross-database access are not covered by ownership chaining. That is my understanding of SQL Server behaviour but it is unverified in this session; the only cited statement is the advice to avoid dynamic SQL.
- The clearest prose statement of the "EXECUTE only" rule comes from an archived 2017 .NET article; the current SQL Server tutorial demonstrates the same behaviour by example rather than stating the rule.
- I did not verify the exact metadata permission (for example VIEW DEFINITION) each tool's introspection needs.

## 5. Tools that generate TypeScript types or wrappers from existing SQL Server stored procedures, and their limits

### Takeaway
I found no maintained Node.js/TypeScript tool that generates typed wrappers from SQL Server stored procedures; the one direct match was last published in 2022, and the PgTyped/sqlc-style tools do not support SQL Server. The underlying SQL Server metadata functions are documented to describe only the FIRST result set and to fail on temp tables and non-literal dynamic SQL, so even a custom generator cannot fully type multi-result-set procedures automatically.

### Cited Findings
- `generator-mssql-types` (Yeoman generator): "inspects your Stored Procedures and generates strongly typed TypeScript code for them." Latest and only line: 0.1.1, published 2022-07-14 (created 2022-06-23). Its TODO notes it cannot tell whether a procedure parameter has a default value "without parsing the procedure definition" (a `sys.parameters` limitation). The README does not describe result-set handling. [raw] — [generator-mssql-types README via registry](https://registry.npmjs.org/generator-mssql-types), [npm page](https://npmjs.com/package/generator-mssql-types)
- `sqlx-ts` 0.49.0 (2026-10-11): "support for PostgreSQL, MySQL, and SQLite"; SQL Server is not listed. [raw] — [sqlx-ts README via registry](https://registry.npmjs.org/sqlx-ts)
- `@pgtyped/cli` latest is 2.4.3 (2025-03-15); PgTyped is a PostgreSQL tool. [raw for version; tool scope from its name/registry listing] — [registry](https://registry.npmjs.org/@pgtyped%2Fcli)
- Prisma TypedSQL: MySQL/PostgreSQL/SQLite only (see question 1). — [Prisma docs, TypedSQL](https://www.prisma.io/docs/orm/prisma-client/using-raw-sql/typedsql)
- Table/view generators exist for SQL Server but do not cover procedures: `kysely-codegen` (mssql dialect) and `@rmp135/sql-ts` ("tables and views"); `mssql-ts` 1.0.6 (2023-12-30) converts schemas to interfaces. [raw for the first two; snippet for mssql-ts] — [kysely-codegen](https://registry.npmjs.org/kysely-codegen), [sql-ts](https://registry.npmjs.org/@rmp135%2Fsql-ts), [mssql-ts on socket.dev](https://socket.dev/npm/package/mssql-ts)
- An npm search for `sp_describe_first_result_set` returned a single package, `@yellicode/reverse-sql` 2.10.0 (2026-07-17), which "Reverse engineers a SQL-Server database and generates C# entities, CRUD actions and stored procedure calls" (C# output, about 30 downloads per month). Searches for SQL Server stored-procedure TypeScript codegen returned no other relevant package. [raw, npm search API] — [npm search](https://registry.npmjs.org/-/v1/search?text=sp_describe_first_result_set&size=12)
- `sp_describe_first_result_set`: "Returns the metadata for the first possible result set of the Transact-SQL batch. ... Raises an error if the Database Engine can't determine the metadata for the first query that will be executed by performing a static analysis." It returns an error when "The statement uses a temporary table" or "The query includes the creation of a permanent table that is then queried"; if possible first statements differ in column count, "an error is thrown and no result is returned"; if they differ in data type an error is thrown (except widening of varchar/nvarchar/varbinary lengths); it "doesn't support indirect recursion". [raw; page updated 2026-10-19, applies to SQL Server 2017 and later] — [Microsoft Learn, sp_describe_first_result_set](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-describe-first-result-set-transact-sql)
- Dynamic SQL: a literal `EXECUTE(N'SELECT a FROM t1')` is discoverable, but a string built in a variable "results in an error. The result isn't discoverable because of the dynamic SQL"; the documented workaround is to declare the shape with `EXECUTE(@SQL) WITH RESULT SETS ((Column1 BIGINT NOT NULL))`. [raw] — [same page](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-describe-first-result-set-transact-sql)
- `sys.dm_exec_describe_first_result_set_for_object` "takes an @object_id as a parameter and describes the first result metadata for the module with that ID" (a T-SQL stored procedure or trigger) and "uses the same algorithm as sp_describe_first_result_set". Microsoft's own example creates `TestProc2` returning two result sets and notes the function "returns information about the first result set in the procedure". Documented error types include `CONFLICTING_RESULTS`, `DYNAMIC_SQL`, `CLR_PROCEDURE`, `EXTENDED_PROCEDURE`, `UNDECLARED_PARAMETER`, `RECURSION`, `TEMPORARY_TABLE` ("the batch contains a temporary table and is not supported") and `UNSUPPORTED_STATEMENT`. A documented pattern lists all procedures with `sys.procedures CROSS APPLY sys.dm_exec_describe_first_result_set_for_object(p.object_id, 0)`. [raw; page updated 2026-11-02] — [Microsoft Learn, sys.dm_exec_describe_first_result_set_for_object](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-exec-describe-first-result-set-for-object-transact-sql)
- Comparable mature tool outside Node.js (shows the ceiling of the technique): EF Core Power Tools (.NET) states "The stored procedure result mapping is limited to what SET FMTONLY can handle, so not all stored procedures are supported", offers `sp_describe_first_result_set` as an alternative, documents a workaround when "#temp tables in your stored procedure ... prevents result set discovery", and says "Support for mapping multiple result sets per procedure is currently in preview." [summ] — [EF Core Power Tools wiki, Reverse Engineering](https://github.com/ErikEJ/EFCorePowerTools/wiki/Reverse-Engineering)

### Inferences
- For this project the generation target is tiny and uniform: 4 procedures whose signatures are identical in every school. Hand-writing 4 typed wrapper functions once (parameter types plus one row type per result set) is cheaper and more reliable than adopting or building a generator. A generator would pay off only with dozens of distinct procedure signatures.
- The documented limits hit this project's procedures specifically: they return multiple result sets (only the first is describable), and school-specific procedures that use temp tables or dynamic SQL are not describable at all.
- A realistic use of these metadata functions here is not codegen but a deployment-time contract check: after installing a school's procedures, query `sys.parameters` and `sys.dm_exec_describe_first_result_set_for_object` to assert that parameter names/types and the first result set's columns match the generic contract. That would catch drift in hand-written school SQL before the API calls it. This is my suggestion, not something found in a source; it only covers the first result set, and it needs a login with rights on the procedures.

### Gaps
- "No maintained tool exists" is a negative result from npm searches and one web search; a private or differently named tool could exist. I did not search GitHub code/topics exhaustively.
- I did not inspect how `generator-mssql-types` derives result types, or whether it handles multiple result sets (its README does not say).
- sqlc and SafeQL were not checked in this session for SQL Server support; my understanding that neither supports it is unverified.
- `sys.parameters` details (what it exposes for procedure parameters) were not fetched directly; only the generator README's remark about missing default-value information is cited.

## 6. What ORM projects and practitioners say about ORMs for reporting/aggregation-heavy queries and legacy or third-party schemas

### Takeaway
The ORM vendors and well-known practitioners agree on the pattern: ORMs are a productivity abstraction for application-owned CRUD models, and aggregation-heavy, window-function or schema-you-do-not-own work belongs in plain SQL through an escape hatch. The strongest directly quotable statements I verified are from Prisma's own documentation and Martin Fowler.

### Cited Findings
- Prisma's "Should you use Prisma ORM?" lists as a poor fit: "... you need full control over all database queries", explaining that "Prisma ORM is an abstraction", that "an inherent tradeoff of Prisma ORM is a reduced amount of control in exchange for higher productivity", and that if workarounds are too costly you "might be better off with a tool that allows you to exercise full control over your database operations using plain SQL", naming plain SQL drivers as the alternative. [summ] — [Prisma docs, Should you use Prisma ORM?](https://www.prisma.io/docs/orm/overview/introduction/should-you-use-prisma)
- Martin Fowler, "OrmHate" (8 May 2012): "The object/relational mapping problem is hard."; an ORM "can handle about 80-90% of the mapping problems" and good ones provide "manholes so you can get down with the SQL when you have to"; where there is no behaviour-rich domain model "you shouldn't think of building a behavior-rich domain model at all", and "One exception that comes to mind is when you're only reading from the database." [summ] — [martinfowler.com, OrmHate](https://martinfowler.com/bliki/OrmHate.html)
- Microsoft's stored-procedure guidance frames the opposite design as a feature: "Client applications do not need to know anything about the underlying data structures. Stored procedure code can be changed without requiring changes in client applications as long as the changes do not affect parameter lists or returned data types." [raw] — [Microsoft Learn, Managing Permissions with Stored Procedures in SQL Server](https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server)
- General practitioner articles repeat a hybrid recommendation: ORM for routine CRUD, hand-written SQL for reporting/analytics, window functions, CTEs and bulk writes. [snippet; secondary blog posts, moderate to low reliability] — [OpenReplay blog, ORM or raw SQL](https://blog.openreplay.com/orm-or-raw-sql/), [OpenReplay blog, ORM wrong tool](https://blog.openreplay.com/orm-wrong-tool/)
- Vendor integration blogs describe a "canonical model above ERP-specific adapters" pattern for multi-ERP integrations, and warn that hard-coded per-customer adapter branches become unmanageable at scale. [snippet; vendor marketing, low reliability] — [Truto blog](https://truto.one/blog/per-customer-data-model-customization-without-code-the-3-level-jsonata-architecture/), [Ampersand blog](https://www.withampersand.com/blog/multi-tenant-erp-integrations-for-ai-products)
- Knex describes itself as "A SQL query builder", not an ORM. [raw] — [knex README via registry](https://registry.npmjs.org/knex)

### Inferences
- The project's workload is close to the worst case for an ORM on every axis the sources name: no domain model of its own in the school database (one table, `pay_order`), logic that is aggregation (SUM/CASE), window functions and a transactional write through the ERP's own number counter, against a schema owned by a third party that changes per school.
- The project already implements the pattern the integration sources recommend: a canonical contract (4 procedures with fixed signatures) above per-ERP adapters (the school-specific procedures). The adapters are written in T-SQL rather than TypeScript, which is what makes the EXECUTE-only login possible.

### Gaps
- I did not find (in this session) direct statements from the Drizzle, Kysely, TypeORM, Sequelize or MikroORM projects about reporting queries or third-party/legacy schemas; their npm READMEs returned nothing relevant to my text searches. Kysely's and Drizzle's well-known positioning as SQL-first query builders was not re-verified from a primary page.
- No conference talk or engineering post from a practitioner running "database per tenant with heterogeneous third-party SQL Server schemas" on Node.js was found. The practitioner evidence here is general, not specific to this architecture.
- Fowler's piece is from 2012 and concerns ORMs in general, not the 2026 TypeScript tools; it is included as the standard practitioner reference, not as current product evidence.

## 7. Verdict: would any of these tools reduce the hand-written per-school SQL, or only relocate it?

### Takeaway
None of the seven would reduce the per-school SQL; at best they relocate it from T-SQL procedures into TypeScript query-builder code while forcing table grants on the API login, per-school schema models and weaker stored-procedure handling. The evidence supports keeping `mssql` plus stored procedures and treating "messy with hundreds of schools" as a SQL source-management problem, which ORMs do not address.

### Cited Findings
- The API login can stay EXECUTE-only because of ownership chaining; table access by an ORM would need table permissions. — [Microsoft Learn, Managing Permissions with Stored Procedures](https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server), [Microsoft Learn, Ownership Chains tutorial](https://learn.microsoft.com/en-us/sql/relational-databases/tutorial-ownership-chains-and-context-switching)
- Only `mssql` returns every result set, output parameters and the return value of a procedure (`result.recordsets`, `result.returnValue`); the ORMs/builders return the first set or one merged array (sources in question 2). — [mssql README](https://registry.npmjs.org/mssql), [typeorm #11566](https://github.com/typeorm/typeorm/issues/11566), [sequelize #8525](https://github.com/sequelize/sequelize/issues/8525), [MikroORM Stored Routines](https://mikro-orm.io/docs/stored-routines)
- The only first-class routine API (MikroORM 7.1+) is experimental, may change in patch releases, and its schema generator manages declared routine bodies as strings (`body`) unless told to ignore them. — [MikroORM Stored Routines](https://mikro-orm.io/docs/stored-routines)
- SQL Server support is absent or pre-release in three of the seven (Prisma 8 RC: none; Drizzle: RC only; Sequelize 7: alpha). — [Prisma docs](https://www.prisma.io/docs/orm/next), [Drizzle latest releases](https://orm.drizzle.team/docs/latest-releases), [sequelize.org v7](https://sequelize.org/v7/)
- Prisma's own guidance points users who need full control of queries to plain SQL drivers. — [Prisma docs, Should you use Prisma ORM?](https://www.prisma.io/docs/orm/overview/introduction/should-you-use-prisma)

### Inferences
- Where the SQL lives: the 90 generic lines and the roughly 200 school-specific lines are procedure bodies inside each school database. No ORM generates T-SQL procedure bodies from a model. MikroORM's routine feature would store the same T-SQL as a string in TypeScript config, which is relocation with a migration engine attached, not reduction.
- If the logic were instead moved into the Node service with a query builder (Kysely, Drizzle, Knex): the same joins, SUM/CASE aggregation and window functions would be rewritten per ERP layout in builder syntax (same volume, different language); each ERP variant would need generated table types; the receipt write would become several round trips in a client-held transaction instead of one procedure call holding the ERP counter lock server-side; and the login would need SELECT/INSERT/UPDATE on ERP tables. Net effect: more code, wider permissions, longer lock windows.
- What actually grows with the number of schools is the count of distinct ERP layouts/customisations, not the count of schools: the generic part is identical everywhere, and schools on the same ERP product can share one adapter script. The levers that reduce mess are therefore on the SQL side (one adapter script per ERP product or version, parameterised per school; scripts in version control; an automated deploy and a contract check per school database). Those are outside the ORM/query-builder category and outside this note's scope.
- On the Node side, the whole typed surface is 4 procedure calls. A single small module with 4 hand-typed wrapper functions over `pool.request().input(...).execute(...)` gives the type safety an ORM would be bought for, with no new dependency.
- A query builder could still be reasonable for a database the team owns (for example a separate control database with its own tables), but that is a different question from the school databases and was not researched here.

### Gaps
- This verdict was not validated by a prototype; it rests on documentation, published source code and issue trackers as of 2026-11-10.
- I did not research SQL deployment, templating or testing tools (for example migration runners or tSQLt-style test frameworks), which is where a reduction in per-school effort would most plausibly come from.
- The claim that school-specific variation clusters by ERP product is an assumption drawn from the project description, not from data about the actual schools.
