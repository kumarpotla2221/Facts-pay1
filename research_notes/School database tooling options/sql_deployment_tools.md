# Tools for versioning and deploying procedures/views/functions to many separate SQL Server databases (state as of 2026-11-10)

## 1. Flyway: repeatable migrations, free edition and SQL Server, 2024-2026 edition changes, many-database rollout, footprint, Java/Docker

### Takeaway
Flyway's repeatable (`R__`) migrations are an exact match for re-runnable `CREATE OR ALTER` files: re-applied only when the file checksum changes, tracked in one history table per database. The engine is Apache-2.0 open source with SQL Server support and an official Docker image; the paid line has collapsed towards Enterprise, and the free Redgate-branded "Community" edition is now described as "for individuals and education", so the safe free choice for a company is the open-source image (`flyway/flyway`).

### Cited Findings
- Repeatable migrations "have a description and a checksum, but no version"; they "are (re-)applied to a database on migrate every time their checksum changes", "always applied last, after all pending versioned migrations", and "in the order of their description (i.e. alphabetically)". Stated uses: (re)creating views/procedures/functions/packages and bulk reference data. "It is your responsibility to ensure the same repeatable migration can be applied multiple times." Adding the `${flyway:timestamp}` placeholder forces a run on every migrate. — [Redgate docs, Repeatable migrations](https://documentation.red-gate.com/fd/repeatable-migrations-273973335.html)
- SQL Server scripts use "Standard SQL syntax with statement delimiter GO"; a script Flyway runs can also be run in sqlcmd/SSMS once placeholders are replaced. The Microsoft JDBC driver ships with the command-line tool; `flyway-sqlserver` artifacts exist for both the Redgate and open-source editions. Page lists "Verified Versions: 2008, 2025". The history table is written to the connection's default schema unless `flyway.schemas` is set. — [Redgate docs, SQL Server database](https://documentation.red-gate.com/flyway/reference/database-driver-reference/sql-server-database)
- Supported-versions page lists SQL Server 2008 through 2025 (2019 and 2022 included). Two support levels: "Supported" = "Certified, with full Redgate Product Support available for Flyway Teams and Flyway Enterprise customers"; "Compatible" = "Limited testing with limited forum support provided by the Flyway community". — [Redgate docs, Supported database versions](https://documentation.red-gate.com/fd/supported-database-versions-143754067.html)
- Flyway V10 (blog dated 20 Nov 2023): "Every user can now download the latest, most secure version of Flyway, however old their database" (previously Community lost support 5 years after a database engine's release); "Flyway Desktop has now been added to the free edition"; "Goodbye OSSifier, welcome plug-in architecture." — [Redgate blog](https://www.red-gate.com/blog/database-devops/why-every-user-can-now-fly-first-class-with-flyway)
- CONFLICT: the Commercial Licensing FAQ ("Page last updated 07 November 2024") still says Community releases are "generally certified for 5 years from its GA (General Availability) release date". It also says Teams/Enterprise "are billed on a 'per user' basis" and Teams is limited to 100 schemas. — [Redgate docs, Commercial Licensing FAQ](https://documentation.red-gate.com/fd/commercial-licensing-faq-181633028.html)
- Editions page (Nov 2026) shows only two editions: Enterprise (28-day trial) and Community, described as "For individuals and education" / "a free database migrations tool for individual developers and education". Teams is not mentioned. Enterprise-only items listed: migration-script generation, undo-script generation, advanced drift detection and reporting, policy-as-code, change reporting, secrets-manager integration. No prices shown. — [Redgate, Flyway editions](https://www.red-gate.com/products/flyway/editions/)
- A reseller page states that since 14 May 2025 Flyway Teams is available only to existing customers (renewals/add-ons). *(search snippet, secondary source)* — [ComponentSource](https://www.componentsource.com/de/product/flyway/licensing)
- The GitHub repo is "Licensed under the Apache License, Version 2.0", supports "50+ DBMS, including: Oracle, SQL Server, MySQL, PostgreSQL", 10.2k stars. README says Flyway Community and Flyway Enterprise "are not part of the Flyway open source project". — [github.com/flyway/flyway](https://github.com/flyway/flyway)
- Open-source Docker image: `docker pull flyway/flyway:13.12.1` (version shown on the page in Nov 2026). — [Redgate docs, Flyway Open Source](https://documentation.red-gate.com/fd/flyway-open-source-277579296.html)
- "The examples below use the `redgate/flyway` image. Open Source Edition users should use `flyway/flyway` instead." "Community edition does not require a license." Teams/Enterprise features are unlocked by a Redgate personal access token in `flyway.toml`. Example: `docker run --rm -v /absolute/path/to/my-flyway-project:/flyway/project redgate/flyway -workingDirectory=project migrate`. — [Redgate docs, Flyway Docker](https://documentation.red-gate.com/fd/flyway-docker-321585710.html)
- The command-line distribution contains a `jre/` folder next to `conf`, `drivers`, `lib`. *(search snippet)* — [Redgate docs, Command-line](https://documentation.red-gate.com/fd/command-line-277579359.html)
- Many databases ("fleet rollout", official tutorial): shared defaults under `[flyway]`, "Under `[environments.<name>]`, add one entry per target with its connection details"; a Bash/PowerShell loop runs `flyway "-environment=$target" info validate migrate` per target and stops at the first failure; per-target variants via `[environments.<name>.flyway] locations = ["filesystem:migrations/common", "filesystem:migrations/variants/eu"]`. On transactional engines (PostgreSQL, SQL Server, Oracle) "the failed target stays at the previous version". After rollout run `flyway info` on every target: "Every target should report the same `Current Version`." The tutorial's examples use `edition: enterprise`; `check -drift`, `check -changes`, `check -dryrun`, `check -code` are used as pre-deployment gates; undo scripts are "a Teams/Enterprise feature". — [Redgate docs, Tutorial - Fleet rollout](https://documentation.red-gate.com/fd/tutorial-fleet-rollout-with-migrations-based-deployment-342852719.html)
- Flyway tracks applied migrations in `flyway_schema_history`; the name can be changed with `flyway.table`. *(search snippet)* — [Redgate, Exploring the Flyway Schema History Table](https://www.red-gate.com/hub/product-learning/flyway/exploring-the-flyway-schema-history-table/)
- Third-party status check: Flyway 13.4.0 shipped August 2026; "Open source core, commercial tiers"; undo scripts in paid tiers. — [Bytebase, Top SQL Server Schema Migration Tools in 2026 (2026-09-09)](https://www.bytebase.com/blog/top-sql-server-migration-tools.md)

### Inferences
- Mapping to this project: `common/R__*.sql` + `schools/<school>/R__*.sql`, one `[environments.<school>]` block generated from `schools.json`, `locations = [common, schools/<school>]`. The existing `CREATE OR ALTER` + `GO` files need almost no change beyond renaming. The `IF OBJECT_ID(...) IS NULL CREATE TABLE pay_order` part can stay repeatable or become `V1__`.
- The core loop (`info validate migrate`, repeatables, environments, history table) uses only core commands, so it should work in the Apache-2.0 open-source edition; the `check -*` gates and undo in the tutorial are paid. Not confirmed by an explicit edition matrix (see Gaps).
- No Java install is needed when Flyway is run from the Docker image; Java is an implementation detail inside the image.
- The history table would land in the ERP's default schema (`dbo`). Renaming it (`flyway.table`) or pointing `flyway.schemas` at an own schema avoids colliding with a vendor who might also use Flyway.
- *(recall, not re-verified)* Flyway refuses to migrate a non-empty schema that has no history table unless `baselineOnMigrate`/`baseline` is used; every ERP database is non-empty, so this setting would be needed on first run.
- SQL Server 2019 passed the old "5 years from GA" Community window in Nov 2024; the V10 blog says the window no longer applies. Treat as "works, but verify with one `flyway info` against a 2019 instance".

## 2. Liquibase: runOnChange / runAlways, free vs paid, licence change, multi-database rollout

### Takeaway
Liquibase handles re-runnable procedures with `runOnChange: true`, but since 5.0 (30 Sep 2025) the free edition is under the Functional Source License rather than Apache 2.0. Internal production use stays free; it is no longer OSI open source. It adds a changelog format on top of plain SQL, which is more ceremony than this project needs.

### Cited Findings
- "The runOnChange changeset attribute runs the change the first time it is detected and each time the changeset is modified." Detection compares the changeset MD5 checksum with the value in `DATABASECHANGELOG`; default false; "runOnChange does not run if you only make changes to whitespace and comments." Without it, a changed changeset raises a checksum error. Recommended for `CREATE OR REPLACE`-style objects so one changeset is kept and source control holds the history. — [Liquibase docs, runOnChange](https://docs.liquibase.com/concepts/changelogs/attributes/runonchange.html)
- `runAlways` executes a changeset on every deployment and updates its existing `DATABASECHANGELOG` row; "Liquibase will throw a checksum error if you modify the contents of an existing runAlways changeset" unless `runOnChange` is also set; "you should use runOnChange instead of runAlways" if the goal is to run only when changed. Intended for permission scripts, tagging, timestamps. — [Liquibase docs, runAlways](https://docs.liquibase.com/concepts/changelogs/attributes/run-always.html)
- Licence: from version 5.0 Liquibase Community is under "Functional Source License, Version 1.1, ALv2 Future License (FSL-1.1-ALv2)"; older versions stay Apache 2.0. FAQ "Can I still use Liquibase Community in production?" — "Yes. Enterprises and developers can continue running Liquibase Community in development, test, and production environments." Forbidden: commercialising it in competition with Liquibase (example: offering it as a managed service). Each release "automatically reverts to Apache 2.0 two years after its release". Liquibase itself says FSL does not meet the OSI definition ("source available"/"fair source"). Contributors sign a CLA from 5.0. Post dated 30 Sep 2025. — [Liquibase blog, FSL](https://www.liquibase.com/blog/liquibase-community-for-the-future-fsl)
- 5.0 release notes repeat: "Liquibase Community is now licensed under the Functional Source License (FSL)." — [Liquibase Community 5.0 release notes](https://docs.liquibase.com/community/release-notes/5-0)
- Community vs Secure (paid): Community has "limited object support" for stored logic, basic rollback (last change / to tag / to date), manual diff only (no drift monitoring), no policy checks, no flow files, forum support. Secure adds advanced stored-logic support, auto-generated/targeted rollback, scheduled drift scans and dashboard, policy checks, flow files, structured logs, SLA support. No prices on the page. — [Liquibase, Community vs Secure](https://www.liquibase.com/community-vs-secure)
- Third-party status check: Liquibase 5.0.4 shipped August 2026; rollback, drift detection and policy checks described as paid features. — [Bytebase (2026-09-09)](https://www.bytebase.com/blog/top-sql-server-migration-tools.md)

### Inferences
- NOTE ON A CONFLICT: one search-engine summary claimed the FAQ answers "No" to production use; the FAQ page itself, read directly, says "Yes". The direct read is authoritative.
- "Limited object support" for stored logic in Community concerns Liquibase's structured change types and snapshots; plain SQL changesets (`sqlFile` + `runOnChange`) are the usual way to ship procedures, so this limit should not block this use case. Not explicitly confirmed on the comparison page.
- Liquibase needs a changelog (XML/YAML/JSON or formatted-SQL headers) describing every file; for five or so `CREATE OR ALTER` files per school this is extra bookkeeping compared with Flyway `R__` naming or grate folders.
- *(recall, not re-verified)* Liquibase is Java-based, has an official Docker image, and creates `DATABASECHANGELOG` and `DATABASECHANGELOGLOCK` in the target database. Multi-database rollout is done the same way as Flyway: one invocation per connection in a loop.

### Gaps
- No Liquibase-published guide for rolling one changelog out to hundreds of databases was found.
- Liquibase Secure pricing not public on the pages read.
- Did not confirm `GO` handling (`endDelimiter`) for SQL Server in the current docs.

## 3. grate (successor of RoundhousE): conventions, hashing, SQL Server, distribution, health

### Takeaway
grate is the closest fit by design: plain SQL files in conventional folders, with `functions/`, `views/`, `sprocs/` treated as "anytime" scripts that re-run only when new or changed, history kept in a `grate` schema inside each database. It is MIT-licensed, actively released (2.2.0 on 5 Nov 2026), and ships as a self-contained Docker image and macOS/Linux binaries, so no .NET install is needed. It is a small community project (about 300 stars).

### Cited Findings
- "grate - the SQL scripts migration runner"; "Database migrations in plain SQL"; MIT licensed; SQL Server (incl. Azure SQL), PostgreSQL, MariaDB/MySQL, SQLite, Oracle; Windows, Linux, macOS; 302 stars, 962 commits, 20 open issues, 6 open PRs. The `erikbra/grate` URL now resolves to `grate-devs/grate`. — [GitHub, grate](https://github.com/erikbra/grate)
- Releases: 2.2.0 dated 05 Nov 2026 (migration correctness fixes, improved Oracle and SQL Server script parsing, a replaced statement-splitting API, `--transaction` now uses `ReadCommitted`; SQL Server fixes include "identifiers containing `GO` are preserved" and a permissions-script hang in transactional migrations); 2.1.6 on 29 Jul; 2.1.5 on 07 Jul (SqlClient 7); 2.0.0 added .NET 10 and dropped .NET 6/7. 2.2.0 makes `gratedevs/grate` the canonical Docker image and ships self-contained zips for Linux, macOS, Windows; its bundled runtime is `.NET 11.0.0-rc.3`. — [GitHub releases](https://github.com/erikbra/grate/releases)
- Script types: one-time scripts "run once per database"; "Anytime scripts, such as views and stored procedures, run when new or changed"; "Everytime scripts, such as permissions and migration hooks, run on every migration." Scripts sort alphabetically within a folder. — [grate docs, home](https://grate-devs.github.io/grate/)
- Default folders in run order: beforeMigration (EveryTime), alterDatabase (AnyTime), runAfterCreateDatabase (AnyTime), runBeforeUp (AnyTime), up (One-time), runFirstAfterUp (AnyTime), functions (AnyTime), views (AnyTime), sprocs (AnyTime), triggers (AnyTime), indexes (AnyTime), runAfterOtherAnyTimeScripts (AnyTime), permissions (EveryTime), afterMigration (EveryTime). Folders can be renamed (`--folders 'up=ddl;views=projections'`) or fully redefined with Type Once/EveryTime/AnyTime. — [grate docs, Folder configuration](https://grate-devs.github.io/grate/folder-configuration/)
- Anytime scripts: "By default, grate runs anytime scripts when they are new or have changed"; "you can't just make it a `create...` script, but should use `create or alter...` instead." — [grate docs, Anytime scripts](https://grate-devs.github.io/grate/script-types/anytime/)
- One-time scripts: "By default, grate fails the migration if a previously run one-time script has changed." `--warnononetimescriptchanges` re-executes and records the new hash; `--warnandignoreononetimescriptchanges` "records the new hash without executing the changed SQL." — [grate docs, One-time scripts](https://grate-devs.github.io/grate/script-types/one-time/)
- Tracking: six tables (`ScriptsRun`, `ScriptsRunErrors`, `Version`, plus `GrateScriptsRun`, `GrateScriptsRunErrors`, `GrateVersion` for grate's own migrations). "All six tables use the same `--schema` setting, which defaults to `grate`" (SQL Server: `grate.ScriptsRun`). `ScriptsRun` records "names, content hashes, script text, one-time flag, and associated `version_id`"; `Version` records versions, timestamps, status and uses the `--version` value passed on the command line. — [grate docs, Migration tables](https://grate-devs.github.io/grate/migration-tables/)
- Distribution: `dotnet tool install -g grate` (needs .NET SDK/runtime); Docker `gratedevs/grate` (Alpine, bundles the .NET runtime; old `erikbra/grate` name kept during transition), configured with `-e APP_CONNSTRING=...` and a `/db` volume; self-contained binaries for Windows x86/x64/Arm64, Linux x64/Arm64 (glibc and musl), macOS x64/Arm64; MSI, Debian packages, Chocolatey, `winget install erikbra.grate`; Homebrew cask in a personal tap "still at 1.8.0"; NuGet libraries `grate.core`, `grate.sqlserver`. — [grate docs, Getting grate](https://grate-devs.github.io/grate/getting-grate/)
- CONFLICT: a Sept 2026 third-party round-up lists grate at "Version 1.6" and calls RoundhousE "no longer under active development". The GitHub release list (primary) shows 2.x. — [Bytebase (2026-09-09)](https://www.bytebase.com/blog/top-sql-server-migration-tools.md)

### Inferences
- Mapping to this project: `up/` for `pay_order` table creation (one-time), `functions/`, `views/`, `sprocs/` for everything else. Per-school objects could be a second grate run with a different SQL directory, or a custom folder list; file names must not collide because history is keyed by script name.
- Passing `--version=<git tag>` gives a per-database answer to "which release does this school have" in `grate.Version`, and `grate.ScriptsRun` gives per-file hashes: this directly addresses the owner's tracking worry without custom code.
- grate creates a `grate` schema in the ERP database (six tables). That is a visible footprint in a third-party database, but it is isolated in its own schema and easy to explain or remove.
- Risk notes: one main maintainer history, about 300 stars, and the 2.2.0 self-contained/Docker builds bundle a release-candidate .NET 11 runtime. Pinning an image tag and testing on a restored copy before upgrading is prudent.
- The fact that grate needed fixes for `GO` inside identifiers in Nov 2026 shows batch splitting is harder than a one-line regex (relevant to section 5).

### Gaps
- Exact column names of `grate.ScriptsRun` not shown on the docs page.
- Did not read the environment-specific scripts page (`/grate/environment-scripts/`), which may offer a cleaner way to hold per-school files.
- Did not verify the minimum SQL Server permissions grate needs (schema creation at least).

## 4. DbUp, sqitch, dbmate, Atlas, Bytebase, SSDT DACPAC / sqlpackage

### Takeaway
None of these fits better than Flyway or grate. dbmate and (per its README) sqitch do not support SQL Server; DbUp needs a .NET host program; Atlas's SQL Server driver and all view/procedure/function support are paid (Pro); Bytebase is a server product capped at 10 instances on the free plan; a DACPAC can technically be limited to a few objects in a third-party database but only by modelling or referencing the vendor schema, which is the heaviest route.

### Inferences
- DACPAC answer to "can it manage only a few objects in a large third-party database?": yes in principle, with defaults (`DropObjectsNotInSource=False`) it will not drop vendor tables or procedures, and a same-database reference keeps vendor objects out of the deployment. But our views/functions reference ERP tables, so the project only builds if the ERP schema is available as an extracted reference dacpac, one per distinct ERP schema version. Combined with the `db_owner` requirement, a .NET SDK build step and a diff engine that reads the whole target schema on every publish, this is overkill for about five objects.
- The `Drop*NotInSource=True` defaults (constraints, indexes, DML triggers, statistics) most plausibly apply to tables that are in the model (here only `pay_order`), not to unmodelled vendor tables; I did not find a source stating this, so it must be tested with `/Action:Script` or `DeployReport` before any real publish.
- Atlas declarative mode would be elegant but is a paid product for SQL Server and for any procedure/view work, with per-database pricing that scales badly to hundreds of schools.
- Bytebase is a hosted/self-hosted server with approvals and review: valuable for DBA teams, more machinery than a two-person team needs, and each on-premise school server would count as an instance against the 10-instance free cap.
- DbUp would force a small C# program into a Node/TypeScript shop; grate gives the same result (it is also .NET) as a ready-made binary.

## 5. Node-native options: Knex, Umzug, or a custom runner on the `mssql` driver, and the pitfalls

### Takeaway
Knex and Umzug track migrations by name and run them once, so they do not natively give "re-run when the file changed"; using them means writing the checksum logic anyway. A custom runner of roughly 100 lines on `mssql` is realistic, but the known traps are `GO` splitting, one-procedure-per-batch, stop-on-error, atomic application plus version row, and concurrency.

### Cited Findings
- "GO is not a Transact-SQL statement; it is a command recognized by the **sqlcmd** and **osql** utilities and SQL Server Management Studio Code editor." "Applications based on the ODBC or OLE DB APIs receive a syntax error if they try to execute a GO command." Syntax is `GO [count]` (batch runs count times); "A Transact-SQL statement cannot occupy the same line as a GO command. However, the line can contain comments."; `GO;` is an error; local variables do not survive a `GO`. — [Microsoft Learn, GO](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/sql-server-utilities-statements-go)
- "The CREATE PROCEDURE statement can't be combined with other Transact-SQL statements in a single batch." `OR ALTER` applies to "SQL Server (starting with SQL Server 2016 (13.x) SP1)". — [Microsoft Learn, CREATE PROCEDURE](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-procedure-transact-sql)
- node-mssql: for `query`, "To execute commands like `create procedure` or if you plan to work with local temporary tables, use batch instead"; `batch` does not use `sp_executesql`. The README does not mention `GO` at all. Option `abortTransactionOnError` "sets the value for `XACT_ABORT` during the initial SQL phase of a connection"; transactions emit `rollback(aborted)`; error code `EABORT` = "Transaction was aborted (by user or because of an error)". — [node-mssql README (12.7.2)](https://cdn.jsdelivr.net/npm/mssql@12.7.2/README.md)
- Even a dedicated tool had splitting bugs: grate 2.2.0 (Nov 2026) replaced its statement-splitting API and fixed "identifiers containing `GO` are preserved". — [grate releases](https://github.com/erikbra/grate/releases)
- sqlcmd: the Go-based sqlcmd "is a standalone tool you can download independently of SQL Server. It runs on Windows, macOS, Linux, and in containers"; the ODBC one is in `mssql-tools`. `-b` "Specifies that **sqlcmd** exits and returns a `DOS ERRORLEVEL` value when an error occurs" (1 when severity > 10); "Using `-V 16` in combination with checking the exit code ... can help catch errors in automated environments". Several switches differ between the Go and ODBC versions. — [Microsoft Learn, sqlcmd utility](https://learn.microsoft.com/en-us/sql/tools/sqlcmd/sqlcmd-utility)
- Knex: state stored in `knex_migrations` (default) with a `_lock` table; "By default, each migration is run inside a transaction"; migrations are JS/TS files exporting `up`/`down`; MSSQL is a supported dialect; no mention of raw SQL files, `GO`, or re-running changed migrations. — [Knex, Migrations](https://knexjs.org/guide/migrations.html)
- Umzug: "Framework agnostic migration tool for Node.js"; custom storage implements `logMigration`, `unlogMigration`, `executed`; migration metadata is `name` (+ optional `path`), no checksum mentioned; SQL files supported through a `resolve` function; 2.2k stars. — [GitHub, umzug](https://github.com/sequelize/umzug)
- Design reference from a hand-built SQL Server tenant rollout engine: each tenant database has a `__schema_migrations` table; each changeset runs in a transaction that checks the table, executes, logs the ID, commits; "Running the same migration script twice must not cause an error or data corruption."; a failed tenant stops, the others continue, and the failed one stays unfixed until someone intervenes. — [51eshare blog (anonymous, circa Oct 2023)](https://ssh-blog.pages.dev/5079348207)
- On SQL Server (a transactional-DDL engine), a failed Flyway target "stays at the previous version". — [Redgate, Fleet rollout tutorial](https://documentation.red-gate.com/fd/tutorial-fleet-rollout-with-migrations-based-deployment-342852719.html)
- Liquibase deliberately ignores whitespace and comment changes when computing whether to re-run. — [Liquibase docs, runOnChange](https://docs.liquibase.com/concepts/changelogs/attributes/runonchange.html)
- Running migrations from application startup causes races and needs schema-altering rights for the app login (said of EF Core `Database.Migrate()`). — [Bytebase (2026-09-09)](https://www.bytebase.com/blog/top-sql-server-migration-tools.md)

### Inferences
- Pitfall checklist for a custom runner (each derived from the findings above):
  1. Split only on lines that consist of `GO` (optionally with a count and a trailing comment), case-insensitively; a naive `split('GO')` breaks on identifiers, strings and comments containing "GO". Decide explicitly whether `GO n` is supported or rejected.
  2. Send each batch with `request.batch()`, not `query()`.
  3. Do not concatenate batches: `CREATE OR ALTER PROCEDURE` must be alone in its batch.
  4. Stop at the first failed batch; sqlcmd without `-b` does not exit on error, and today's manual `sqlcmd` runs may have been silently partial.
  5. Atomicity: run all batches of a release plus the insert/update of the version row in one transaction with `XACT_ABORT ON`, so a school is either fully on the new hash or fully on the old one.
  6. Checksum: hash file bytes after normalising line endings (CRLF vs LF changes the hash); store per file: name, hash, applied-at, app/git version.
  7. Concurrency: take a lock (for example `sp_getapplock`) so two deploys or two app instances cannot apply at once.
  8. Fleet behaviour: per-school result recorded centrally (success/failed/unreachable), continue-or-halt policy decided up front, and a re-run must be a no-op for schools already on the current hash.
  9. Use a separate login with DDL rights for deployment; do not give the payment service's runtime login `ALTER` rights just to self-migrate.
- A middle path that avoids writing a `GO` parser: have the Node deploy script shell out to Microsoft's sqlcmd (`-b -V 16 -i file.sql`) inside the Docker image and only add the hash/version bookkeeping around it. The cost is that sqlcmd's batches are not wrapped in one transaction unless the file itself does it.
- Knex/Umzug add a dependency without solving the changed-file problem; they are a poor fit for repeatable objects. No maintained Node equivalent of `node-pg-migrate` with SQL Server repeatable semantics turned up in searches.

### Gaps
- No authoritative Node-specific write-up on `GO` splitting was found; Stack Overflow material appeared only as search snippets.
- Knex and Umzug behaviour for edited migrations is inferred from the absence of checksum features in their docs, not from an explicit statement.

## 6. Multi-tenant practice: rolling objects out to hundreds of tenant databases

### Takeaway
The recurring pattern across sources is: one shared script set, an idempotent per-database history table, a loop over a tenant list, canary first and then waves, sequential or bounded-parallel execution with an explicit halt-or-continue policy, and a post-rollout report of every tenant's version. Most public write-ups are vendor guides; candid first-hand accounts for SQL Server at this scale are rare.

### Cited Findings
- Redgate (Flyway) fleet guidance: apply to one low-risk production target first with the same command, smoke-test and watch for at least one monitoring window; then waves such as 10%, 50%, 100% with pauses; sequential, fail-fast loop; fix forward with a new migration; for single-target drift capture the manual change as a migration and run `flyway repair`; never edit the history table by hand; run `flyway info` on all targets afterwards and keep the output as an audit artifact; avoid per-target variants for cosmetic differences because each one multiplies the test matrix. — [Redgate docs, Fleet rollout tutorial](https://documentation.red-gate.com/fd/tutorial-fleet-rollout-with-migrations-based-deployment-342852719.html)
- Atlas database-per-tenant guide: `deployment` groups evaluated in order ("the first matching group wins"), canary group then a `rest` group with `depends_on`; `parallel` defaults to 1 and should be sized to instance capacity; `on_error` `FAIL` ("Stop the group's execution immediately on first error") or `CONTINUE`; tenants discovered by a `data "sql"` query against a management database; re-running after a partial rollout is safe; per-database status via `atlas cloud database list` (`SYNCED`/`PENDING`/`FAILED`). — [Atlas, Staged rollout guide](https://www.atlasgo.io/guides/database-per-tenant/rollout)
- Hand-built SQL Server engine for "hundreds of isolated SQL Server tenant databases": "A simple `migrate up` command across all tenants simultaneously was a non-starter."; Git as source of truth; per-tenant `__schema_migrations`; tenants processed one at a time to protect the servers; canary by percentage; failures logged loudly but do not stop other tenants; admits "Engineers currently have to rely on structured logs and querying the `__schema_migrations` tables" to see fleet state, and that rollback is not automated. Unsigned personal blog, approx. Oct 2023; the Kafka/Nacos architecture is far larger than this project needs. — [51eshare blog](https://ssh-blog.pages.dev/5079348207)
- Turso (2 June 2025, Jamie Barton): database-per-tenant "turns every schema change into a coordination nightmare"; proposes pull instead of push: each client checks a registry of versioned SQL scripts and applies what it is missing "at its own pace", which suits offline or intermittently reachable databases. SQLite context. — [Turso blog](https://turso.tech/blog/how-to-deploy-schema-changes-to-a-million-databases)
- Microsoft's database-per-tenant sample (Wingtip Tickets) uses Elastic Jobs with target groups to run T-SQL across all tenant databases and a template database for new tenants, with job status per database in a job-agent database. Azure SQL Database only; article dated 2018 and now archived. — [Microsoft Learn (archived)](https://learn.microsoft.com/en-us/previous-versions/sql/database/saas-tenancy-schema-management?view=azuresql)
- General guidance: test in staging, deploy to a small canary subset, monitor, then full rollout; record migration history and status. *(search snippet)* — [Bytebase, Multi-tenant database architecture patterns](https://www.bytebase.com/blog/multi-tenant-database-architecture-patterns-explained.md)
- General guidance: each tenant database has its own migrations table and a central registry maps tenant to version; new tenants are initialised at the current head; bounded parallelism with a circuit breaker. *(search snippet)* — [Backend Engineering Essentials](https://alivedise.github.io/backend-engineering-essentials/multi-tenancy/schema-migrations-in-multi-tenant-systems)

### Inferences
- For this project the practices reduce to five small things: (1) a history/version table in every school database; (2) a deploy command that takes "one school", "a named group" or "all"; (3) always deploy to dev (SQL Server 2022) then one friendly school before the rest; (4) sequential execution with a per-school result line; (5) a `status` command that prints school, version/hash, applied-at for all schools, optionally mirrored into a central table so unreachable schools are visible.
- This case differs from textbook database-per-tenant: the schema is not ours and the school-specific objects differ per school, so "every tenant reports the same version" becomes "every tenant reports the current hash of common + its own file". Drift detection should also cover the dependency side: an ERP upgrade can break a view without any change on our side, so a cheap smoke query per school (for example `EXEC sp_refreshsqlmodule` or calling each view with `TOP 0`) is worth more than object-diff tooling. This is my suggestion from prior knowledge, not from a source read in this session.
- Firewalled on-premise schools make a central push loop fail for exactly those tenants. Since the payment service must already reach each school database to work at all, deploy tooling can use the same network path; where no inbound path exists, the Turso-style pull model (a small job at the school pulling the current script set) is the documented alternative.
- Ordering: common part before school-specific part; within Flyway that is alphabetical description order, within grate folder order then alphabetical.

### Gaps
- No named-company post-mortem on SQL Server database-per-tenant rollout at hundreds of databases was found; the only SQL Server-specific first-hand source is an unsigned blog.
- No source addressed the specific situation of installing a few objects into third-party (vendor-owned) tenant databases.

## 7. Testing stored procedures: tSQLt and alternatives, practicality on a restored third-party backup

### Takeaway
tSQLt works on any SQL Server database, including a restored ERP backup, and its `FakeTable` isolates procedures from vendor data, but it needs sysadmin, CLR and a server certificate on the test instance, must never be in production, and has had no packaged release since 2022. For a Node team, integration tests from Vitest/Jest against a SQL Server container with the restored backup are the lower-machinery alternative.

### Cited Findings
- "tSQLt is a unit testing framework for Microsoft SQL Server"; Apache 2.0; "compatible with SQL Server 2005 (service pack 2 required) and above on all editions"; 466 stars, 2,342 commits, 78 open issues. — [GitHub, tSQLt](https://github.com/tSQLt-org/tSQLt)
- Install: run `PrepareServer.sql` once per server (needs SA; it "automatically enables CLR" and installs a server certificate); "There is no need to disable strict CLR security on the server."; then "execute the tSQLt.class.sql script ... in your development database". "tSQLt should never be installed in production." — [tSQLt quick start](https://tsqlt.org/user-guide/quick-start/)
- "FakeTable creates an empty version of the table without the constraints in place of the specified table."; "When the test case completes, the original table is put back in place because of the rollback which tSQLt performs at the end of each test case."; "FakeTable cannot be used with temporary tables"; "if you are faking a table, you are not testing the constraints on the table." — [tSQLt, FakeTable](https://tsqlt.org/user-guide/isolating-dependencies/faketable/)
- Latest packaged release V1.0.8043.39707, dated 2022 (sources disagree on the month); a third-party review says the repository still receives commits in 2026 and the framework works on current SQL Server versions. *(search snippets)* — [tSQLt release notes](https://tsqlt.org/release-notes/), [Bytebase, SQL Server SQL review tools 2026](https://www.bytebase.com/blog/top-sql-server-sql-review-tools.md)
- Node alternative: `@testcontainers/mssqlserver` is documented together with the `mssql` driver; restoring a `.bak` in a container is done by copying the file in and running `RESTORE DATABASE ... FROM DISK ... WITH MOVE`. *(search snippets)* — [Testcontainers for Node, MSSQL Server module](https://node.testcontainers.org/modules/mssqlserver), [Stack Overflow mirror: import .bak to SQL Server test container](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/72186681/import-bak-file-to-sql-server-test-container)
- Atlas's own testing framework is a Pro (paid) feature. — [Atlas features](https://atlasgo.io/features)

### Inferences
- Practicality on a restored third-party backup: feasible. tSQLt installs into the restored copy (its own `tSQLt` schema), `FakeTable` swaps ERP tables for empty constraint-free copies inside a transaction that is rolled back, so tests are deterministic and independent of the school's real rows. The costs are a second language for tests (T-SQL), sysadmin/CLR setup on the dev server or container, and keeping tSQLt strictly out of the deploy scripts.
- Lower-machinery alternative that matches the stack: in Vitest/Jest, connect with `mssql` to the dev SQL Server 2022 container holding the restored school backup, apply `common.sql` + `<school>.sql` with the same runner used for deployment, then call the procedures inside a transaction and roll back. This also tests the deployment path itself, which tSQLt does not.
- Two caveats when testing on restored backups: (1) *(recall, not re-verified)* a backup from SQL Server 2019 restores onto 2022 but not the reverse, so dev (2022) cannot produce backups for schools; (2) school backups contain personal data of pupils and parents, so they need the same care as production or should be scrubbed.
- With one small team and about five procedures per school, a handful of integration tests per school-specific procedure (fee lookup returns expected shape; payment posting is idempotent) gives most of the value; a full tSQLt suite is optional.

### Gaps
- Could not confirm from a primary source that tSQLt's CLR assembly installs cleanly on SQL Server 2022 Linux containers.
- No write-up found on testing custom procedures specifically against restored vendor (ERP) databases.

## 8. Overall fit for a tiny team (synthesis of the objective)

### Takeaway
Three options are proportionate: grate, open-source Flyway, or a small custom runner; all three reduce to "plain SQL files + a history table per school + a loop over `schools.json`". Liquibase is workable but heavier; DACPAC, Atlas and Bytebase are overkill or paid for this case; DbUp, sqitch, dbmate, Knex and Umzug are poor fits.

### Cited Findings
- Hash-based re-run of procedure/view/function files without any config language is native in grate (folder convention) and Flyway (`R__` prefix). — [grate docs](https://grate-devs.github.io/grate/script-types/anytime/), [Flyway docs](https://documentation.red-gate.com/fd/repeatable-migrations-273973335.html)
- Both ship self-contained Docker images (`gratedevs/grate`, `flyway/flyway`). — [grate docs, Getting grate](https://grate-devs.github.io/grate/getting-grate/), [Flyway Docker docs](https://documentation.red-gate.com/fd/flyway-docker-321585710.html)
- Licences: grate MIT; Flyway engine Apache 2.0; Liquibase Community FSL-1.1-ALv2 since 5.0; Atlas SQL Server driver Pro-only. — [grate GitHub](https://github.com/erikbra/grate), [Flyway GitHub](https://github.com/flyway/flyway), [Liquibase FSL post](https://www.liquibase.com/blog/liquibase-community-for-the-future-fsl), [Atlas features](https://atlasgo.io/features)

### Inferences
| Option | Fit | Why (short) |
|---|---|---|
| grate | Good fit | Plain SQL, `sprocs/views/functions` re-run on hash change, `--version` recorded per DB, MIT, single Docker image or binary. Small project; pin versions. |
| Flyway open-source (`flyway/flyway`) | Good fit | `R__` repeatables, `[environments.*]` per school, `info` for reporting, largest user base, Apache 2.0. Needs baseline setting on non-empty ERP DBs; paid features not needed. |
| Custom Node runner (`mssql`) | Good fit if kept to about 100 lines | No new tool, same language, full control over school list and reporting. Team owns `GO` splitting, transactions, locking. |
| Custom wrapper around `sqlcmd -b` | Acceptable | Keeps today's workflow, adds only hash/version bookkeeping; weaker atomicity. |
| Liquibase Community | Workable, heavier | `runOnChange` does the job; changelog files and FSL licence add friction with no benefit here. |
| DACPAC / sqlpackage | Overkill | Needs the vendor schema as a reference model, `db_owner`, .NET build; state-diff engine pointed at a database we do not own. |
| Atlas | Overkill and paid | SQL Server and procedures/views are Pro-only; per-database pricing. |
| Bytebase | Overkill | Server product with approvals; free plan capped at 10 instances. |
| DbUp | Poor fit | Requires writing a C# host; no hash-based re-run without custom code. |
| Knex / Umzug | Poor fit | Name-based run-once tracking; would still need custom checksum logic. |
| sqitch / dbmate | Not applicable | No SQL Server support per their READMEs. |

- Decision rule: if the team wants zero custom code, pick grate or Flyway (grate if folder conventions and a per-DB version label appeal; Flyway if a larger community and longevity matter more). If the team prefers no new runtime or tool at all, write the small runner and follow the pitfall checklist in section 5.
- Whichever is chosen, the same three additions fix the owner's actual worry: a per-school history table, a one-school-first rollout habit, and a `status` report across all schools.

### Gaps
- No head-to-head benchmark or independent comparison of grate vs Flyway for SQL Server repeatable objects was found; the recommendation rests on documented behaviour, not field reports.
