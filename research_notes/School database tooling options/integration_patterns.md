## 1. Which established patterns apply, and how do connector-based products split "connector" from "per-customer configuration"?

### Takeaway
The problem is a textbook Anti-Corruption Layer / adapter-per-source-system with a small canonical model: every integration product surveyed (Airbyte, Singer, Merge, Flywire, Dynamics eConnect) writes code once **per external product** and expresses each customer as **data** (a validated config object, a mapping, or a settings record), never as a copy of the code. The project's fixed two-procedure contract already is the canonical model; what is missing is the middle "per ERP product" layer between "generic" and "per school".

### Cited Findings
- **Anti-Corruption Layer (ACL).** "Implement a facade or adapter layer between different subsystems that don't share the same semantics. This layer translates requests that one subsystem makes to the other subsystem... Eric Evans first described this pattern in *Domain-Driven Design*." It applies to "any external system that your development team doesn't control." **[V]** — [Azure Architecture Center, Anti-Corruption Layer pattern, ms.date 2026-05-28](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer)
- ACL direction of translation: "Communication between subsystem A and the anti-corruption layer always uses the data model and architecture of subsystem A. Calls from the anti-corruption layer to subsystem B conform to that subsystem's data model or methods. The anti-corruption layer contains all the logic necessary to translate between the two systems. You can implement the layer as a component within the application or as an independent service." **[V]** — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer)
- ACL considerations listed by Microsoft that are relevant here: "Consider whether you need more than one anti-corruption layer"; "Make sure that you maintain and monitor transaction and data consistency"; "consider enforcing input validation and sanitization at this boundary"; "Plan for observability, including correlation IDs and structured logging, to diagnose translation failures"; and "focus the anti-corruption layer on translation logic. Avoid placing business rules or orchestration in the layer." **[V]** — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer)
- **Canonical Data Model (Enterprise Integration Patterns, Hohpe & Woolf, 2003).** Problem: "How can you minimize dependencies when integrating applications that use different data formats?" Solution: "design a Canonical Data Model that is independent from any specific application." The page's worked numbers: direct translation needs 2, 6 and 30 translators for 2, 3 and 6 applications; with a canonical model 4, 6 and 12. It notes the approach can look heavy with only a few applications and pays off as the count grows; a new application only needs translation to and from the common model. **[R]** — [enterpriseintegrationpatterns.com, Canonical Data Model](https://www.enterpriseintegrationpatterns.com/patterns/messaging/CanonicalDataModel.html)
- **Airbyte: one connector per source system, customer = config validated against a schema.** Standard commands: `spec` ("allows an actor to broadcast information about itself and how it can be configured"), `check` (validates that "given a configuration" the actor can connect), `discover`, `read`. The config is a JSON object that must validate against the connector's `connectionSpecification` (a JSON Schema); Airbyte renders that schema as a form. A source is an application for one kind of data store: "the Postgres Source is a Source that pulls from Postgres." **[R]** — [Airbyte Protocol docs](https://docs.airbyte.com/understanding-airbyte/airbyte-protocol)
- **Airbyte: declarative connectors are preferred over hand-written ones.** Options listed: Connector Builder (recommended for API sources), Low-Code CDK (connector described in YAML, optional custom Python components), Python CDK, which "provides the most flexibility to developers" but "requires the most code and maintenance." A community TypeScript CDK (Faros.ai) exists but is not officially supported ("use them with caution"). **[R]** — [Airbyte connector development](https://docs.airbyte.com/connector-development/)
- **Singer: same shape.** A tap is invoked as `tap --config CONFIG [--state STATE] [--catalog CATALOG]`; the config "contains whatever parameters the Tap needs in order to pull data from the source", is JSON, and "will vary by Tap." **[R]** — [Singer SPEC.md](https://github.com/singer-io/getting-started/blob/master/docs/SPEC.md)
- **Merge.dev (unified API): three layers — common model, integration, linked account.** Field Mapping can be defined "across an integration" ("map fields that are not Common Model fields to all Linked Accounts for that integration") or for "a specific Linked Account" ("map a custom field that is specific to a Linked Account"). **[R]** — [Merge docs, Field Mapping overview](https://docs.merge.dev/merge-unified/supplemental-data/field-mapping/overview)
- Merge limits per-customer overrides on the **write** path: "The Common Model override feature only supports GET use cases. If a Common Model field is overridden, you will no longer be able to POST data to that field." **[X]** — [Merge help centre, Field Mapping guide](https://help.merge.dev/articles/5129286502-field-mapping-guide)
- **Flywire (tuition payments ↔ student information systems/ERPs) — the closest commercial analogue found.** Its developer site lists one connector guide **per SIS/ERP product, each separately versioned**: Banner (Ethos cloud connector v1.9, on-premise connector v3.0), Colleague (cloud v1.7, on-premise v1.6), PeopleSoft (on-premise only, v2.4), Workday Student (cloud only, v1.10). "Cloud connectors use APIs available for your SIS/ERP and require no installation on your servers"; "On-Premise connectors are installed on your server." Functions are a fixed small contract across all connectors: RTSI (pull "student information, transactions, balances, and other data from your system") and RTPN (send payment information back to the institution's system). For non-standard systems: "If you are using a home grown system, you can work with Flywire to develop a custom SFS integration" (a generic API integration guide v2.0). **[R]** — [Flywire developer docs, SFS Connectors](https://developers.flywire.com/education/Content/sfs-connectors.htm)
- Flywire markets "pre-built, certified integrations with Ellucian Banner, Ellucian Colleague, Oracle PeopleSoft, Workday Student, Unit4, Anthology Student, and Tribal Group" (vendor marketing claim). **[X]** — [Flywire partner page](https://www.flywire.com/industries/education/partners/ellucian)
- **Microsoft Dynamics GP eConnect — an ERP vendor's own integration layer is stored procedures inside the ERP database.** "The business objects are a collection of SQL stored procedures installed on the Microsoft Dynamics GP server. eConnect uses the business objects to perform all retrieve, create, update, and delete operations." The architecture diagram "shows that an integrating application can bypass the API layer and use the eConnect business objects directly." (Archived doc, 2014.) **[V]** — [Microsoft Learn (archived), eConnect architecture](https://learn.microsoft.com/en-us/previous-versions/dynamicsgp/developer/aa973837(v=msdn.10))
- **Dynamics 365 Finance & Operations data entities — vendor-supplied abstraction over physical tables.** "A *data entity* is an abstraction from the physical implementation of database tables... the abstraction also insulates application code from the inevitable churn of the physical tables between versions." **[V]** — [Microsoft Learn, Data entities overview, ms.date 2026-04-03](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/data-entities/data-entities)
- **Codat (unified accounting API) — per-customer account mapping as data.** After a customer authorises, "you can use the bank accounts endpoint to retrieve a list of accounts which can be mapped enabling the user to dictate which account their payments should be reconciled to", and similarly the user chooses "which GL account income and any platform fees should be recorded against." **[X]** (the receivables page returned HTTP 404 when fetched directly, so wording is unconfirmed) — [Codat docs, automating payables](https://docs.codat.io/usecases/summary/automating-payables), [automating receivables](https://docs.codat.io/usecases/summary/automating-receivables)

### Inferences
- Mapping to this project: the README contract (`pay_get_dues` → three result sets; `pay_mark_paid` → receipt number or `THROW 50001/50013`) **is** the canonical data model; `common.sql` is the generic layer on the application side of the ACL; each ERP's implementation of the two procedures is the ACL adapter. The three-level split used by every product above translates to: **generic** (contract + `common.sql` + app), **per ERP product** (adapter SQL written against that product's schema), **per school** (a handful of values). Today's layout has only generic and per-school, so product logic and school constants are mixed in `ranchi.sql`.
- Airbyte's `spec` idea transfers cheaply: each ERP adapter should declare the settings it needs (name, type, required/default), and a school's values should be validated against that list before deploy. The project already depends on `zod` **[L]**, so this needs no new library.
- "Canonical model" here should stay as small as it is. Microsoft's warning to keep business rules out of the ACL argues against moving generic logic (order state machine, expiry) into the per-ERP adapters; it belongs in `common.sql`, which is where it already is **[L]**.
- Flywire's "custom integration for home-grown systems" is the escape hatch to copy: a school on an unknown or one-off ERP gets its own adapter file under the same contract. The pattern does not require every school to fit a shared adapter.
- Merge restricting overrides to reads is a useful design signal: per-customer variation on the **write** path is where vendors are most conservative. For this project that suggests per-school overrides of `pay_mark_paid` logic should be rare and explicit, while display labels and read-side breakdown can vary freely.

### Gaps
- I found no public engineering write-up from a fee-collection or payment product describing direct SQL integration with on-premise school ERP databases (as opposed to vendor APIs). Flywire's integration guides are password-protected for clients, so its per-institution configuration detail is unknown.
- I did not find documentation of integration APIs for Indian school ERP products; whether the specific ERP in use ("Metas school ERP" per `ranchi.sql`) offers an API or import tables was not researched.
- No definition of "Linked Account"/"Common Model" was quoted on the Merge page fetched; the three-layer reading is mine, from the two mapping levels the page does state.

## 2. "One adapter per ERP product + per-customer settings" versus "one script per customer": maintenance cost and how differences are expressed

### Takeaway
Authoritative guidance and practitioner accounts agree: per-customer code copies stop scaling at roughly ten customers because every fix must be re-applied and re-tested N times; the standard remedy is one codebase per variant-family plus per-customer **data**. Hard numbers on cost are scarce; the evidence is consistent but qualitative.

### Cited Findings
- Microsoft lists as a multitenant **antipattern**: "Specialized customizations for tenants: Avoid deploying features or a configuration that only applies to a single tenant. This approach adds complexity to your deployments and testing processes. Instead, use the same resource types and codebase for each tenant." **[V]** — [Azure Architecture Center, deployment and configuration of multitenant solutions, ms.date 2025-07-16](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/deployment-configuration)
- Same page, second antipattern: "Manual deployment and testing: Manual deployment processes add risk and slow your ability to deploy", and on consistency: "Manual processes introduce the chance of error or inconsistent steps across tenants. Your environment can then be left in an inconsistent state, which makes it harder for your team to manage the solution." **[V]** — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/deployment-configuration)
- Scale thresholds Microsoft gives: plan differently for "only a few tenants, such as five or fewer" versus many; keeping the tenant list as pipeline **configuration** (a parameters file edited by hand) "works well for small numbers of tenants" but "as the number of tenants increases, often around 10 or more, it becomes cumbersome"; treating tenants as **data** with a control plane "is often much more time-consuming to build. Your effort needs to be justified by the number of tenants." The worked example is a company with six tenants and dedicated databases per tenant growing to 300. **[V]** — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/deployment-configuration)
- Feature flags are **not** the recommended vehicle for permanent per-customer differences: flags are for progressively exposing features; for selectively enabling things for specific customers "Feature flags aren't usually the right choice... Instead, consider building a process to track and enforce the *license entitlements* that each customer has." **[V]** — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/deployment-configuration)
- Practitioner account (Ian Johnson, DEV Community; year not shown on page): separate deployed instances per customer "works for two or three customers and collapses by ten"; tenant-ID conditionals in code are "Cheap on day one, untenable by month six"; the recommended shape is "separating, cleanly and firmly, the code that defines what behaviors are possible from the data that selects and parameterizes them" so that "To add a new tenant configuration, you change data." Storage advice: "Use the database you already have"; static baked-in config is "Fine for values that genuinely never change between deploys"; and "Do not store executable code in the configuration." **[R]** — [DEV Community, "Custom behavior without custom code"](https://dev.to/tacoda/custom-behavior-without-custom-code-4l9g)
- Practitioner opinion (Julien Danjou, Mergify, 2026-09-08): "Every customer got the same decisions because maintaining a version per customer was impossible"; SAP customers "share maybe 80% of the system and diverge completely after that"; "ERP migrations take years because of that customization, and custom code remediation is the biggest variable in the schedule." He also notes successful vendor customisation seams work "by putting your changes somewhere the vendor never has to merge." **[R]** — [julien.danjou.info, "Every customer gets the same software"](https://julien.danjou.info/blog/every-customer-gets-the-same-software/)
- Dissenting/forward-looking view in the same post: Danjou argues AI-assisted maintenance may make carrying per-customer variants cheap ("The customization penalty that made per-customer software ruinous evaporates" if that holds), while admitting "I think it holds. I've been wrong before" and that his company does not do it yet. **[R]** — [julien.danjou.info](https://julien.danjou.info/blog/every-customer-gets-the-same-software/)
- Airbyte's own ranking of hand-written versus declarative connectors: the Python CDK "requires the most code and maintenance"; the declarative YAML route is recommended. **[R]** — [Airbyte connector development](https://docs.airbyte.com/connector-development/)
- How per-customer differences are expressed in the products surveyed: Airbyte — a JSON config validated against the connector's JSON-Schema spec, passed in on every command **[R]** ([Airbyte Protocol](https://docs.airbyte.com/understanding-airbyte/airbyte-protocol)); Singer — a JSON config file passed with `--config` **[R]** ([Singer spec](https://github.com/singer-io/getting-started/blob/master/docs/SPEC.md)); Merge — mappings stored per integration and per linked account **[R]** ([Merge docs](https://docs.merge.dev/merge-unified/supplemental-data/field-mapping/overview)); SQL Server database projects — SQLCMD variables whose "values... are set at deployment time" **[V]** ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/tools/sql-database-projects/concepts/sqlcmd-variables)); Flyway — "Rather than maintaining separate migrations per environment, you can specify a placeholder token e.g. ${schema} which Flyway will resolve to a value at runtime" **[X]** ([Redgate Flyway placeholders](https://documentation.red-gate.com/fd/placeholders-configuration-224003082.html)).
- ERP products themselves keep per-installation settings in **one-record parameter tables inside the customer database**: D365's "Parameter" entity category covers "Tables that contain only one record, where the columns are values for settings." **[V]** — [Microsoft Learn, Data entities overview](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/data-entities/data-entities)
- What actually varies in the existing school file **[L]**: in `/Volumes/Xcode/facts/schools-sql/ranchi.sql` the literal school code `'01'` appears on 6 code lines; the bank name `'HDFC  Bank A/c No 50200049075959'` and bank ledger code `'171'` once each (line 188-189); the cashier label `'Online (Facts Pay)'` once; the IST offset `330` minutes once; two display labels (lines 88-89). Ledger account codes are **not** hard-coded: they are derived from the ERP's own tables via the view `pay_ledger_acct_v` and the ERP flags `particulars.onlinestudentfee` / `onlinetransportfee`.

### Inferences
- A concrete three-layer split consistent with all sources above:
  - **Generic** (one copy): the contract, `common.sql`, the Node service, the contract test suite.
  - **Per ERP product** (one adapter per product, e.g. `adapters/metas/adapter.sql`): `pay_get_dues`, `pay_mark_paid` and helper views/functions written against that product's schema, plus a declared list of settings the adapter needs.
  - **Per school** (data only): the setting values (school code, bank name, bank ledger code, cashier label, time-zone offset, labels) and the entry in `schools.json` naming the adapter and its version.
  - A school on a different ERP = a new adapter under the same contract. A school whose customisation cannot be expressed as a setting = an explicit override of one named helper (for example its own `pay_ledger_acct_v`), not a fork of the adapter.
- Where the ERP already stores the fact (which account is the student ledger, which particular is the online-fee particular), read the ERP's own configuration instead of adding a setting. `ranchi.sql` already does this for account codes **[L]**; it is the cheapest form of per-school variation because it needs no data from us at all.
- Timing: by my count roughly ten literals in a 207-line file are school-specific **[L]**; everything else is ERP-product logic. Extracting them is a small edit, and can wait until the second school on the same ERP is actually onboarded; doing it then also reveals which "constants" really differ between two real installations. Until then the single file is not yet a maintenance problem. The Microsoft thresholds (≤5 manual is fine, ~10 becomes cumbersome) support deferring heavier machinery (control plane, self-service onboarding) well beyond that.
- "Feature flags" are the wrong word for this project's needs. Permanent differences between schools are settings; a flag is only justified for rolling a new adapter version out to one school before the rest.
- "Settings passed by the application on each call" (the Airbyte/Singer model) versus "settings stored in the customer database" is a real choice for SQL Server; see question 3 for the trade-off. The connector frameworks choose application-side config because their connectors are stateless processes; that reason does not automatically carry over when the adapter is a stored procedure behind an EXECUTE-only login.
- Danjou's contrarian point is relevant to a very small team using AI coding tools: per-school files are cheaper to *write* than they used to be. It does not remove the *verification* cost (each file writes money records into a different live ERP), which is why a shared adapter plus a shared test suite still wins once two schools share a product.

### Gaps
- No quantitative study of maintenance cost for per-customer scripts versus shared adapters was found; all evidence is qualitative guidance or opinion.
- softwareengineering.stackexchange.com ("How do you organize highly customized software?") could not be fetched by the tool, so the widely-cited practitioner answers there are not included.
- A search excerpt attributed to reintech.io claims "every request that you can solve with configuration instead of code saves hundreds of hours of future maintenance"; the page was not opened and the figure is unsupported, so it is not relied on.

## 3. SQL Server: ways to parameterise one shared script per database without copying it

### Takeaway
Four mechanisms exist and they solve different problems: a **one-row settings table** (values, read at run time, identical procedure text everywhere), **sqlcmd/SqlPackage variables or other deploy-time templating** (values or identifiers baked into the text at deploy), **synonyms** (only object *names/locations*), and **procedure parameters** from the app. For values such as school code and bank ledger, a settings table or deploy-time substitution both work with ownership chaining and an EXECUTE-only login; the project already deploys with `sqlcmd -i`, so `-v name=value` costs nothing extra.

### Cited Findings
**sqlcmd scripting variables**
- "Scripting variables enable one script to be used in multiple scenarios. For example, if you want to run one script against multiple servers, instead of modifying the script for each server, you can use a scripting variable." They are defined "explicitly by using the `setvar` command, or implicitly by using the `sqlcmd -v` option", and environment variables are also read. **[V]** — [Microsoft Learn, Use sqlcmd with scripting variables, ms.date 2025-07-02](https://learn.microsoft.com/en-us/sql/tools/sqlcmd/sqlcmd-use-scripting-variables)
- Precedence, low to high: system environment variables; user environment variables; shell `SET X=Y`; `sqlcmd -v X=Y`; `:Setvar X Y`. So a `:setvar` inside the script **overrides** a `-v` on the command line. **[V]** — [Microsoft Learn](https://learn.microsoft.com/en-us/sql/tools/sqlcmd/sqlcmd-use-scripting-variables)
- Substitution is textual and works for identifiers as well as values: the documented example is `SELECT x.$(ColumnName) FROM Person.Person x` run with `sqlcmd -v ColumnName ="FirstName" -i c:\testscript.sql`. **[V]** — [Microsoft Learn](https://learn.microsoft.com/en-us/sql/tools/sqlcmd/sqlcmd-use-scripting-variables)
- Undefined variables: "If a script references a variable that isn't an environment variable or isn't defined by using `setvar`, an error message is returned and the execution of the script stops"; but the same page's example F shows that without `-b` the statement still runs with the literal text `$(tablename)` and only prints "'tablename' scripting variable not defined", and "If `-b` is set, **sqlcmd** will terminate after the 'variable not defined' error." **[V]** — [Microsoft Learn](https://learn.microsoft.com/en-us/sql/tools/sqlcmd/sqlcmd-use-scripting-variables)
- Quoting: values with spaces must be quoted; embedded quotation marks must be escaped (`:setvar MyVar "spac""e"`). **[V]** — [Microsoft Learn](https://learn.microsoft.com/en-us/sql/tools/sqlcmd/sqlcmd-use-scripting-variables)
- The project's deploy script already runs each file with `sqlcmd ... -b -d ranchi_school -i /tmp/<file>.sql`. **[L]** — `/Volumes/Xcode/facts/tools/restore-ranchi.sh` lines 9 and 25-27

**SQLCMD variables in SQL database projects / SqlPackage (deploy-time templating, Microsoft's packaged form)**
- "SQLCMD variables are used in SQL projects to create dynamically replaceable tokens in SQL objects and scripts. The values of these variables are set at deployment time." Supplied with `SqlPackage /Action:Publish ... /v:EnvironmentName=production` or a publish profile. **[V]** — [Microsoft Learn, SQLCMD variables in SQL projects, ms.date 2026-03-11](https://learn.microsoft.com/en-us/sql/tools/sql-database-projects/concepts/sqlcmd-variables)
- Missing values: the project page says a default "isn't compiled into the `.dacpac` file and a command line deployment without the values specified... results in empty values for the SQLCMD variables" **[V]** ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/tools/sql-database-projects/concepts/sqlcmd-variables)); the SqlPackage reference says of `/Variables:` "An error results if a value is not provided for every variable" **[V]** ([Microsoft Learn, SqlPackage Deploy Report and Drift Report](https://learn.microsoft.com/en-us/sql/tools/sqlpackage/sqlpackage-deploy-drift-report)). The two statements conflict; behaviour should be tested rather than assumed.
- Flyway offers the same idea as `${placeholder}` tokens set by environment variable, config or API, usable in versioned and repeatable migrations; Redgate warns one of its placeholder-generation features "is not SQL aware" (plain text matching). **[X]** — [Redgate Flyway placeholders](https://documentation.red-gate.com/fd/placeholders-configuration-224003082.html)

**Synonyms**
- A synonym "Provides an alternative name for another database object... that can exist on a local or remote server" and "Provides a layer of abstraction that protects a client application from changes made to the name or location of the base object." Base objects may be tables, views, stored procedures and functions. **[V]** — [Microsoft Learn, Synonyms (Database Engine)](https://learn.microsoft.com/en-us/sql/relational-databases/synonyms/synonyms-database-engine)
- Late binding: "The binding between a synonym and its base object is by name only. All existence, type, and permissions checking on the base object is deferred until run time." Dangling references "will only be found at run time." There is "no ALTER SYNONYM statement" (drop and re-create). **[V]** — [Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/synonyms/synonyms-database-engine)
- Limits: synonyms are "not schema-bound" and cannot be used in schema-bound views/functions, CHECK constraints or computed columns; "You cannot reference a synonym in a DDL statement"; GRANT/DENY/REVOKE on a synonym "are associated only with the synonym and not the base object." **[V]** — [Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/synonyms/synonyms-database-engine)

**Query-plan consequences of each way of supplying a value**
- A constant in the query text: "SQL Server can use the value of the constant with full trust." A procedure parameter: "SQL Server does not know the run-time value, but it 'sniffs' the input value when compiling the query." A local variable: "SQL Server has no idea at all of the run-time value, and applies standard assumptions" (for example a 30 % hit-rate for an inequality). Copying a parameter into a local variable loses the sniffed value. **[R]** — [Erland Sommarskog, "Slow in the Application, Fast in SSMS?", revision 2026-10-17](https://www.sommarskog.se/query-plan-mysteries.html)
- With `OPTION (RECOMPILE)` "the values of local variables are considered." **[R]** — [Sommarskog](https://www.sommarskog.se/query-plan-mysteries.html)
- A stored procedure's cache entry "is not tied to a certain session or user, but it is global to all connected users"; SET options and the database id are among the cache keys, so the same text in different databases gets separate plans. **[R]** — [Sommarskog](https://www.sommarskog.se/query-plan-mysteries.html)

**Permission consequences**
- Ownership chaining: "If all objects in the chain of execution have the same owner, then SQL Server only checks the EXECUTE permission for the caller, not the caller's permissions on other objects." **[V]** — [Microsoft Learn (archived .NET doc, 2017), Managing Permissions with Stored Procedures](https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server)
- Chaining covers SELECT, INSERT, UPDATE, DELETE, MERGE and EXECUTE only. It does **not** cover dynamic SQL (a separate, ownerless scope), operations needing stronger permissions (for example `TRUNCATE TABLE` "requires ALTER permission on the table"), metadata access through catalog views/`object_id()` (needs VIEW DEFINITION), or cross-database access unless explicitly enabled (off by default). **[R]** — [Erland Sommarskog, "Packaging Permissions in Stored Procedures", revision 2026-03-15](https://www.sommarskog.se/grantperm.html)
- Microsoft's training material states the same for dynamic SQL: it "executes outside of the context of the calling stored procedure, so the ownership chain is broken", so the caller needs direct rights on the tables used. **[X]** — [Microsoft Learn training module, database and object permissions](https://learn.microsoft.com/en-us/training/modules/configure-database-authentication-authorization/5-describe-database-object-permissions)
- Application locks are already per database: "SQL Server uses the current database ID to qualify the resource. Therefore, if `sp_getapplock` is executed, even with identical parameter values on different databases, the result is separate locks on separate resources." `@Resource` is "binary-compared, and thus is case-sensitive"; permission needed is membership in `public`. **[V]** — [Microsoft Learn, sp_getapplock, ms.date 2026-06-19](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql)

### Inferences
Comparison (my synthesis; "plan" and "permission" rows follow from the cited facts above):

| Mechanism | What it can vary | Procedure text across schools | Plan effect | Permission effect | Main risk |
|---|---|---|---|---|---|
| One-row settings table in the school DB (`pay_settings`), read by the procedures | Values only | Byte-identical, so one hash identifies the adapter version | If read into local variables the optimiser cannot see the value (generic estimates); harmless for a column with one distinct value such as `school_code`, otherwise join/sub-select the settings row inline or add `OPTION (RECOMPILE)` | Static SQL on a same-owner table: covered by ownership chaining, EXECUTE-only login still works; the API login gets no rights on the table | The row is per-database state that can be edited by hand or be missing; needs a NOT NULL/CHECK-constrained single row and a check at deploy |
| `sqlcmd -v` / `:setvar` / SqlPackage `/v:` / Flyway placeholders (deploy-time text substitution) | Values **and** identifiers (table, column, schema names) | Differs per school after rendering; drift check must compare against the rendered text or stamp a version | Values become constants in the text: best case for the optimiser | No change: still static SQL, chaining applies | Textual substitution into SQL: quoting mistakes and injection-shaped bugs at deploy time; silent `$(var)` literals if `-b` is omitted; the deployed text no longer equals the file in git |
| Synonyms | Object name/location only (a table that is named differently, or lives in another schema/database) | Identical | None expected (resolved to base object) | Permission checks on the base object are deferred to run time; whether an unbroken chain is preserved through a synonym was not verified | Cannot fix differing columns or constants; breakage only surfaces at run time |
| Parameters passed by the Node app on each call (from `schools.json`) | Values only | Identical | Parameters are sniffed | The EXECUTE-only login can now choose accounting values (for example the bank ledger code) | Weakens the "API can only do what the procedures allow" boundary; `pay_mark_paid` is called by `pay_settle`, so values would have to be threaded through the generic procedure |

- The two leading options combine well: keep the adapter text identical per ERP product and let the deploy step write the settings row from a per-school values file in the repo (via `sqlcmd -v` in a tiny seeding script, or a parameterised `MERGE`). Git stays the source of truth, the procedures stay byte-identical, and the per-school "file" shrinks to a handful of values.
- Deploy-time substitution is the only option of the four that can vary identifiers, which is what a *customised* installation of the same ERP may need (an extra column, a renamed table). That is a reason to keep it available as the override mechanism but not to use it for plain values.
- sqlcmd variables are a client-side feature. From prior knowledge (not verified in this session): the Node `mssql` driver does not interpret `:setvar`, `$(var)`, `:r` includes or `GO` batch separators, so scripts using them must be run through `sqlcmd` (as the project does today **[L]**) or rendered by the project's own code before being sent.
- Also from prior knowledge, unverified here: sqlcmd's `:r <file>` include command would let a five-line per-school wrapper set variables and then include the shared product script.
- Because plan-cache entries are keyed by database id, sharing one adapter text across many school databases on one server does not make schools share (or fight over) a plan.
- Avoid the tempting fifth option, dynamic SQL inside the procedure built from settings (table names in a config row): it breaks ownership chaining, so the EXECUTE-only login would need table grants or the procedures would need certificate signing.

### Gaps
- Sommarskog's article (in the portion read) covers a parameter copied to a local variable, not specifically a value selected from a settings table into a variable; I treat the two as equivalent for estimation, which is an inference.
- Whether ownership chaining passes through a synonym to a same-owner base table was not confirmed from a primary source.
- The conflicting Microsoft statements about a missing SqlPackage variable ("empty values" versus "an error results") were not resolved.
- DbUp's variable substitution was searched for but no result was returned; not covered.

## 4. Logic in the customer's database (procedures, EXECUTE-only login) versus logic in the application (SQL in TypeScript, table grants)

### Takeaway
For a write that must be atomic with ERP tables, use the ERP's own counter and run under least privilege in a database the team does not own, sources favour procedures in the customer database: Microsoft describes it as a "security perimeter", and an ERP vendor (Dynamics GP eConnect) built its own integration layer exactly this way. The costs are the ones Fowler listed in 2003 and they are real: SQL logic is harder to modify, test and version, and deployed copies can drift from the application.

### Cited Findings
**For procedures in the database**
- "One method of creating multiple lines of defense around your database is to implement all data access using stored procedures or user-defined functions. You revoke or deny all permissions to underlying objects, such as tables, and grant EXECUTE permissions on stored procedures. This effectively creates a security perimeter around your data and database objects." **[V]** — [Microsoft Learn (archived, 2017), Managing Permissions with Stored Procedures](https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server)
- Listed benefits include: "users can access data and objects only in ways that developers and database administrators intend"; "Ad hoc queries and data modifications can be disallowed"; "Client applications do not need to know anything about the underlying data structures. Stored procedure code can be changed without requiring changes in client applications as long as the changes do not affect parameter lists or returned data types"; "Stored procedures can reduce network traffic by combining multiple operations into one procedure call." **[V]** — [Microsoft Learn (archived)](https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server)
- Demonstrated in Microsoft's tutorial: a user with no table rights gets "The SELECT permission was denied on the object 'PurchaseOrderHeader'" on a direct query, yet "can access the base tables through the stored procedure" because procedure and tables have the same owner. **[V]** — [Microsoft Learn, Tutorial: Ownership Chains and Context Switching](https://learn.microsoft.com/en-us/sql/relational-databases/tutorial-ownership-chains-and-context-switching)
- When chaining is not enough (dynamic SQL, DDL, cross-database), Sommarskog calls certificate signing "preferable in most cases", says `EXECUTE AS` "appears at first glance to be a lot easier to use, but this is a mirage", and warns that marking a database TRUSTWORTHY "can introduce a major security vulnerability on your server." **[R]** — [Sommarskog, "Packaging Permissions in Stored Procedures", rev. 2026-03-15](https://www.sommarskog.se/grantperm.html)
- Microsoft best-practice list for this model: "Avoid dynamic SQL unless absolutely necessary"; "Create parameterized stored procedures that validate all user input"; "Do not add users or roles to the `sysadmin` or `db_owner` roles." **[V]** — [Microsoft Learn (archived)](https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server)
- Vendor precedent: Dynamics GP eConnect's business objects "are a collection of SQL stored procedures installed on the Microsoft Dynamics GP server", used "to perform all retrieve, create, update, and delete operations." **[V]** — [Microsoft Learn (archived, 2014), eConnect architecture](https://learn.microsoft.com/en-us/previous-versions/dynamicsgp/developer/aa973837(v=msdn.10))
- Atomic write next to ERP tables, as implemented today: `pay_settle` opens one transaction, locks the order row (`UPDLOCK, HOLDLOCK`), calls the school's `pay_mark_paid`, marks the order `PAID`, and rolls everything back on any error; `pay_mark_paid` takes a per-student `sp_getapplock` with `@LockOwner = 'Transaction'` and increments the ERP's receipt counter in the same transaction. **[L]** — `/Volumes/Xcode/facts/schools-sql/common.sql`, `/Volumes/Xcode/facts/schools-sql/ranchi.sql`
- Transaction-owned application locks "are released when the transaction commits or rolls back", and with owner `Transaction` the call "must be executed from within a transaction." **[V]** — [Microsoft Learn, sp_getapplock](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql)
- The project already tests the perimeter: "the web login can run the pay procedures but cannot touch a table or write a receipt directly." **[L]** — `/Volumes/Xcode/facts/test/pay.test.ts` line 114

**For logic in the application**
- Fowler ("Domain Logic and SQL", February 2003): "Modifiability is probably the main reason why people put business logic in memory"; "If most of a team is less comfortable with SQL, then that's a reason to keep domain logic away from SQL"; "If you want portability keep logic out of SQL"; "Common practice in SQL seems to not test"; "it's not uncommon to find essential views and stored procedures not even held in configuration management tools." **[R]** — [martinfowler.com, Domain Logic and SQL](https://martinfowler.com/articles/dblogic.html)
- Fowler on the other side of the same trade: complex SQL in his example ran "twenty times faster" than the in-memory approaches, and on encapsulation "The biggest issue here is with updates, which often can't be done properly with views... This is why many shops wrap all DML with stored procedures." **[R]** — [martinfowler.com](https://martinfowler.com/articles/dblogic.html)
- The ACL may live on either side: "You can implement the layer as a component within the application or as an independent service", with the reminder to "maintain and monitor transaction and data consistency." **[V]** — [Azure Architecture Center, Anti-Corruption Layer](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer)
- Doing a multi-statement write from Node is supported by the driver the project uses (`mssql` ^12.7.14 **[L]**, `/Volumes/Xcode/facts/package.json`): "always use `Transaction` class to create transactions" because "it ensures that all your requests are executed on one connection"; "Once you call `begin`, a single connection is acquired from the connection pool." Stored procedures are called with `request.execute`, and multiple result sets arrive as `result.recordsets`. **[R]** — [tediousjs/node-mssql README](https://github.com/tediousjs/node-mssql)
- Without procedures the login needs direct rights: with dynamic or ad hoc SQL "the user account running the dynamic SQL must have rights to the tables and views" used. **[X]** — [Microsoft Learn training module](https://learn.microsoft.com/en-us/training/modules/configure-database-authentication-authorization/5-describe-database-object-permissions)

### Inferences
- When experienced teams choose **in-database procedures**: (a) the write must be atomic with third-party tables and use a counter row inside that database; (b) the database belongs to someone else and its owner wants to read exactly what an outside service may do — a short list of procedures is auditable, a set of table grants is not; (c) the SQL is necessarily specific to that database's schema anyway, so nothing is gained by keeping it far from the schema; (d) the vendor itself exposes procedures (eConnect). All four hold for this project.
- When they choose **application-side SQL**: (a) they are not allowed to create objects in the customer database, or an ERP upgrade/restore wipes non-vendor objects; (b) the integration is read-only; (c) the team wants a single deployment artefact, type-checked and unit-tested in one language; (d) many databases must be upgraded simultaneously and a per-database deploy step is the bottleneck. With hundreds of schools (d) becomes the real cost of the procedure approach, and (a) is a risk to ask each ERP vendor about.
- Security delta if logic moved to TypeScript: the login would need SELECT on the dozen or so ERP tables read, INSERT on the two receipt tables and UPDATE on the counter table. A leaked credential could then insert arbitrary receipts or read all student financial data, where today it can only run the four granted procedures with their built-in checks.
- Atomicity delta: the same transaction is possible from Node via `sql.Transaction`, but it becomes several network round trips while holding the counter-row and application locks, and a crash or timeout mid-way depends on connection teardown to roll back. In-procedure, it is one round trip with `XACT_ABORT ON` **[L]**.
- Deployment/versioning delta is the genuine weakness of procedures: application SQL is always the version that shipped with the app; procedures are a second artefact per database that can be stale, hand-edited or lost in a restore. This is what the version handshake and drift checks in question 5 are for.
- A hybrid keeps the benefits and removes most of Fowler's objections: the adapter SQL lives in the application repository, is deployed by a repeatable idempotent script (`CREATE OR ALTER`, as today **[L]**), is tested by the same vitest suite, and reports its version to the app. The logic runs in the database; the lifecycle is owned by the application.
- Static SQL only inside adapters. The moment an adapter needs dynamic SQL, the EXECUTE-only model needs certificate signing, which is disproportionate for a very small team.

### Gaps
- The Microsoft "security perimeter" page is an archived 2017 .NET Framework document; I did not find a current Microsoft Learn page stating the same recommendation as strongly, though the ownership-chain tutorial (current) demonstrates the mechanism.
- No source was found that measures failure rates or incident data for either approach; the "when teams choose each" list is inference from the cited trade-offs.
- Whether the school ERP's vendor or the schools' IT policies permit third-party procedures in the ERP database (and whether ERP upgrades preserve them) is unknown and should be asked per ERP product.

## 5. Contract testing for adapters, and detecting drift in a deployed customer database

### Takeaway
The industry model is one shared, generic test suite that every adapter must pass, configured by a small per-adapter file with optional golden records (Airbyte's Connector Acceptance Tests), plus periodic checks against the live external system (Fowler's contract tests). SQL Server supplies cheap building blocks for drift detection (`sys.dm_sql_referenced_entities`, `sp_describe_first_result_set`, SqlPackage reports), each with a limitation that matters here.

### Cited Findings
**Shared suite per adapter**
- Airbyte's Connector Acceptance Tests are a shared suite run against every connector to "ensure a minimum quality bar" (conformance to the Airbyte specification). Test classes: `spec`, `connection`, `discovery`, `basic_read`, `full_refresh`, `incremental`, plus attribute/documentation checks. Each connector supplies only a small `acceptance-test-config.yml`; inapplicable tests must be skipped with an explicit `bypass_reason`. **[R]** — [Airbyte, Connector Acceptance Tests reference](https://docs.airbyte.com/connector-development/testing-connectors/connector-acceptance-tests-reference)
- Golden-record comparison in the same suite: `basic_read` can point `expect_records` at an `expected_records.jsonl` file; produced records are compared against it, order-insensitively unless `exact_order` is set. **[R]** — [Airbyte](https://docs.airbyte.com/connector-development/testing-connectors/connector-acceptance-tests-reference)
- The first version of these suites is now deprecated and kept as "Standard Tests (Legacy)". **[R]** — [Airbyte](https://docs.airbyte.com/connector-development/testing-connectors/connector-acceptance-tests-reference)
- Fowler's contract test (2011, renamed 2018): tests that "check that all the calls against your test doubles return the same results as a call to the external service would"; "the format of the data matters rather than the actual data"; they need not run in the deployment pipeline — their rhythm follows changes in the external service, and about once a day is usually enough; a failure means updating the double and possibly the code. **[R]** — [martinfowler.com, ContractTest](https://martinfowler.com/bliki/ContractTest.html)
- The project already has the seed of such a suite: `/Volumes/Xcode/facts/test/pay.test.ts` covers lookup ("returns student + dues in integer paise, breakdown lines sum to each due"), the full payment flow (tampering, expiry, replay) and least privilege, run against a restored copy of the school's database (`/Volumes/Xcode/facts/tools/restore-ranchi.sh`, `/Volumes/Xcode/facts/database_backup/09112026RanchiSchool.bak`). **[L]**

**tSQLt**
- `tSQLt.FakeTable` "creates an empty version of the table without the constraints in place of the specified table", works on tables, views and synonyms, "cannot be used with temporary tables", and the original is put back because tSQLt rolls back the transaction at the end of each test case. **[R]** — [tSQLt user guide, FakeTable](https://tsqlt.org/user-guide/isolating-dependencies/faketable/)
- Other documented features (names verified, descriptions not on the page read): `NewTestClass`, `SpyProcedure`, `FakeFunction`, `ApplyConstraint`, `AssertEqualsTable`, `AssertResultSetsHaveSameMetaData`, `AssertEqualsTableSchema`, `ExpectException`. **[R]** — [tSQLt user guide](https://tsqlt.org/user-guide/)
- Installation constraints: "To install, execute the tSQLt.class.sql script... in your development database"; `PrepareServer.sql` "automatically enables CLR and installs a server certificate that allows the installation of the tSQLt CLR"; "Executing the script requires SA permission, but needs to be done only once per server"; and "tSQLt should never be installed in production." **[R]** — [tSQLt quick start](https://tsqlt.org/user-guide/quick-start/)

**Checking a deployed database**
- `sys.dm_sql_referenced_entities('schema.proc','OBJECT')` "Returns one row for each user-defined entity that is referenced by name in the definition" of a module, including column-level dependencies and whether each is selected or updated (`is_selected`, `is_updated`), `is_select_all`, and `is_insert_all` ("The object is used in an INSERT statement without a column list"). **[V]** — [Microsoft Learn, sys.dm_sql_referenced_entities, ms.date 2026-08-21](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-sql-referenced-entities-transact-sql)
- It exposes breakage after a schema change: it "Returns error 2020 when column dependencies cannot be resolved", with the message that the entity "references an object that does not exist or... an error in one or more statements in the entity"; `is_all_columns_found = 0` marks the affected object and `is_incomplete = 1` marks "a binding error" (SQL Server 2016 SP2+). Microsoft's Example D shows a procedure that references a non-existent table being created successfully and only this function reporting the problem. **[V]** — [Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-sql-referenced-entities-transact-sql)
- Its permission need: "VIEW DEFINITION permission on the referencing entity." **[V]** — [Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-sql-referenced-entities-transact-sql)
- `sp_describe_first_result_set` "Returns the metadata for the first possible result set of the Transact-SQL batch" (name, type, length, nullability per column) by static analysis, and guarantees that execution either errors, returns nothing, or "returns a first result set with the same metadata". It errors if "The statement uses a temporary table" or the result depends on non-literal dynamic SQL; it needs "permission to execute the *@tsql* argument." Only the **first** result set is described. **[V]** — [Microsoft Learn, sp_describe_first_result_set, ms.date 2025-10-23](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-describe-first-result-set-transact-sql)
- SqlPackage: "The SqlPackage DeployReport action creates an XML report of the changes that would be made by a publish action. The SqlPackage DriftReport action creates an XML report of the changes that have been made to the registered database since it was last registered." Related publish options: `BlockWhenDriftDetected` ("block updating a database whose schema no longer matches its registration or is unregistered") and `DropObjectsNotInSource` (whether objects absent from the .dacpac are dropped from the target). **[V]** — [Microsoft Learn, SqlPackage Deploy Report and Drift Report, ms.date 2025-07-30](https://learn.microsoft.com/en-us/sql/tools/sqlpackage/sqlpackage-deploy-drift-report)
- Metadata is outside ownership chaining: access through catalog views or `object_id()` needs VIEW DEFINITION and is not covered by the chain. **[R]** — [Sommarskog, "Packaging Permissions in Stored Procedures"](https://www.sommarskog.se/grantperm.html)
- Extended properties can carry descriptive data on database objects and "Because the property is stored in the database, all applications that read the property can evaluate the object in the same way." **[V]** — [Microsoft Learn, Synonyms (Database Engine)](https://learn.microsoft.com/en-us/sql/relational-databases/synonyms/synonyms-database-engine)

### Inferences
- **Shared contract suite.** Turn the existing vitest file into a suite parameterised by school (Airbyte's model): the generic tests assert the contract (three result sets with the exact column names and types; `lines` sum to each due; unknown admission number yields an empty first result; `pay_mark_paid` raises `DUES_CHANGED` on a changed amount and `BUSY` on lock timeout; one payment moves the ERP counter by exactly one and drops the balance by exactly the paid amount; any error leaves no rows behind). Each school contributes only a small fixture file: database name, a few known admission numbers and their expected dues. A test that cannot apply to a school must be skipped with a stated reason, never silently.
- **Golden results are the right tool for the refactor that matters most here.** Before turning `ranchi.sql` into a parameterised product adapter, capture `pay_get_dues` output for a sample of real admission numbers on the restored backup; after the change the output must be identical. The same captured file then protects every later adapter change for that school. This is characterisation testing, and it catches exactly the bug class that hand-written per-school SQL produces.
- **Two different cadences**, following Fowler: the suite runs on every change against restored backups in Docker (fast, safe); a lightweight read-only probe (`pay_get_dues` for a designated test student plus the version check below) runs daily against each live school, because the thing that changes without notice is the ERP, not our code.
- **tSQLt is optional for this team.** It must be installed into the database under test, needs CLR and sysadmin on the server, and must never go into a school's production database; it therefore only fits the restored copies, where the existing Node suite already runs. Its distinctive value (`FakeTable` to isolate a procedure from hundreds of ERP tables) would matter if restores became too slow or too large to keep per school; until then, one test runner is simpler than two.
- **Version handshake.** Add one generic procedure (for example `pay_adapter_info`, granted to the role) returning contract version, adapter name, adapter version and a content hash. The app compares it at start-up and in the daily probe and refuses payments (not lookups) on mismatch. Because the API login has no VIEW DEFINITION and metadata is not covered by ownership chaining, the hash should be **stamped as a literal at deploy time** (deploy-time substitution, or a row in the settings table written by the deploy script) rather than computed at run time from `sys.sql_modules`.
- **Schema-change detection.** A deploy/admin-side check (run with a login that has VIEW DEFINITION, not the API login) can loop over the `pay_*` modules with `sys.dm_sql_referenced_entities` and fail on error 2020 / `is_all_columns_found = 0` / `is_incomplete = 1`. It detects dropped or renamed tables and columns after an ERP upgrade before a parent hits the error. It does not detect *added* NOT NULL columns or changed semantics; the daily probe and the fail-closed guards in the write path cover those.
- `sp_describe_first_result_set` alone cannot verify `pay_get_dues`, which returns three result sets; from Node it is simpler to execute the procedure for a non-existent admission number and assert the column metadata of all three (empty) result sets. From prior knowledge, unverified in this session: the `mssql` driver exposes per-recordset column metadata.
- SqlPackage DriftReport fits poorly: it needs the database registered as a data-tier application and compares the whole schema, whereas here the database is the vendor's (hundreds of tables) and only a dozen objects are ours. A hash of our own objects is the proportionate tool.

### Gaps
- tSQLt's website gave feature names without descriptions on the page read and showed no current release information ("©2010 - 2020" footer); its maintenance status and SQL Server 2022/2025 support were not verified.
- No primary source was found describing a published "contract test suite per customer database" practice for SQL-level adapters specifically; the approach above is transferred from connector frameworks.
- I did not verify how `sys.dm_sql_referenced_entities` behaves through views and scalar functions nested inside a procedure (the adapter uses both); each module may need to be checked individually.

## 6. Writing into a third-party ERP's tables safely

### Takeaway
The safest order of preference is: the vendor's supported API or import/staging tables, then the vendor's own procedures, and only then direct inserts shaped like records the ERP itself produces. Where direct inserts are unavoidable, the standard protections are an idempotency key checked inside the same transaction, a staging/inbox record of our own, fail-closed guards, and automated detection of vendor schema change. The project already implements the first three.

### Cited Findings
**Prefer the vendor's surface**
- D365 F&O: integrations go through data entities; when data management is enabled an entity gets a "Staging table... used in asynchronous integrations and high-volume scenarios", and the entity "insulates application code from the inevitable churn of the physical tables between versions." **[V]** — [Microsoft Learn, Data entities overview](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/data-entities/data-entities)
- Dynamics GP: the vendor ships stored-procedure "business objects" in the ERP database for all create/update/delete operations, and an integrating application may call them directly. **[V]** — [Microsoft Learn (archived), eConnect architecture](https://learn.microsoft.com/en-us/previous-versions/dynamicsgp/developer/aa973837(v=msdn.10))
- SAP Business One: SAP Community answers citing SAP Note 896891 state that SAP "will not support any database, which is inconsistent, due to SQL-Queries, which modify datasets or the datastructure of the SAP Business One Database"; direct INSERT/UPDATE/DELETE is tolerated only on plain user-defined tables; the DI API is the sanctioned write path; one commenter also warns of licence issues. **[X]** (the note itself was not retrieved and the SAP blog returned HTTP 403) — [SAP Community thread](https://answers.sap.com/questions/86313/how-to-update-oinm-table-value.html), [SAP blog, "Guidelines for modifying SAP Business One data", 2016](https://blogs.sap.com/2016/07/28/guidelines-for-modifying-sap-business-one-data/)
- Flywire's connectors post payments back to the institution's system through a named real-time interface (RTPN) rather than ad hoc writes. **[R]** — [Flywire developer docs](https://developers.flywire.com/education/Content/sfs-connectors.htm)

**Idempotency**
- Stripe: idempotency keys exist "for safely retrying requests without accidentally performing the same operation twice"; the client generates the key ("we suggest using V4 UUIDs"); for API v1 Stripe "saves the status code and body of the first request made with a given idempotency key" and "Retries with the same key return the saved response, including `500` errors"; "The idempotency layer compares incoming parameters to those of the original request and errors if they're not the same"; keys can be pruned "after they're at least 24 hours old." **[V]** — [Stripe API reference, Idempotent requests](https://docs.stripe.com/api/idempotent_requests)
- The project's equivalent: `order_id` is a UUID primary key in `pay_order`; `pay_settle` locks that row, refuses `PAID` orders with `50011 ORDER_ALREADY_PAID`, and writes the receipt and the `PAID` status in one transaction "So the receipt and the order can never disagree, and a double click can never produce two receipts." **[L]** — `/Volumes/Xcode/facts/schools-sql/common.sql`, `/Volumes/Xcode/facts/schools-sql/README.md`

**Staging / inbox / outbox**
- Transactional Outbox: the problem is "How to atomically update the database and send messages to a message broker?"; the solution stores the message in a table in the same local transaction and a separate relay forwards it; "Messages are guaranteed to be sent if and only if the database transaction commits"; the relay may deliver more than once, so the consumer must be idempotent (for example by tracking processed message IDs). **[R]** — [microservices.io, Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)
- The project already has one table of its own in each school database (`pay_order`, "the only table we add") holding every attempt with status, amount and a JSON snapshot of what the parent saw. **[L]** — `/Volumes/Xcode/facts/schools-sql/common.sql`
- The current adapter leaves the receipt **unposted** (`cr_no = 0`): "The balance drops at once and the accountant posts it to the bank (cr_no) exactly as for a counter receipt." It also shapes the row "like the ERP's existing 'Online' receipts." **[L]** — `/Volumes/Xcode/facts/schools-sql/ranchi.sql` header comment

**Concurrency and counters**
- `sp_getapplock` return codes: 0 granted, 1 granted after waiting, -1 timed out, -2 cancelled, -3 deadlock victim, -999 parameter/call error; "A deadlock with an application lock doesn't roll back the transaction that requested the application lock", so return values must be checked. **[V]** — [Microsoft Learn, sp_getapplock](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql)
- The adapter takes the receipt number with a single `UPDATE document SET @doc_no = next_no, next_no = next_no + 1` inside the transaction and throws `FR_COUNTER_MISSING` unless exactly one row was updated; it throws `PARTICULAR_MISSING` if the inserted line count is wrong. **[L]** — `/Volumes/Xcode/facts/schools-sql/ranchi.sql` lines 177-203

**Risk when the vendor changes the schema**
- A procedure that references a missing table can exist without error until it runs (Microsoft's Example D creates `dbo.Proc1` selecting from a non-existent `Table1`); the dependency function then reports error 2020. **[V]** — [Microsoft Learn, sys.dm_sql_referenced_entities](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-sql-referenced-entities-transact-sql)
- The same function flags `is_insert_all` for an "INSERT statement without a column list". **[V]** — [Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-sql-referenced-entities-transact-sql)
- Microsoft's ACL guidance for any boundary with a system you do not control: "Make sure that you maintain and monitor transaction and data consistency" and "Plan for observability, including correlation IDs and structured logging, to diagnose translation failures." **[V]** — [Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer)

### Inferences
- **Ask each ERP vendor first.** For every new ERP product the first onboarding question should be whether it has an API, import tables, or its own "save receipt" procedure. If the ERP's desktop client saves receipts through a stored procedure, calling that procedure from the adapter is safer than re-creating its inserts, because vendor upgrades then carry the adapter along. The SAP example shows that some vendors withdraw support for databases modified by outside SQL; a school's support contract may contain a similar clause, which is a commercial risk as much as a technical one.
- **Direct inserts, when unavoidable, should imitate a record type the ERP already produces and leave the ERP's own posting step to the ERP.** The Ranchi adapter does both (existing "Online" receipt shape; accountant posts it). That is effectively the staging pattern using the ERP's own "unposted" state: our write is limited to the same two tables a counter clerk's receipt touches, and the ledger posting logic we do not understand is never bypassed.
- **A stricter alternative exists and is worth naming even if not chosen:** write only to `pay_order` and let a scheduled job or the ERP's import post receipts. It removes web-path writes to ERP tables but loses the immediate receipt number and balance update, adds a job to run on every school's server, and adds a failure mode (paid but not yet receipted). For a very small team the present synchronous design is simpler and already atomic; the alternative becomes attractive only for an ERP whose vendor forbids direct writes.
- **Fail closed on anything unexpected.** The existing `@@ROWCOUNT` guards are the right idiom: every statement that assumes "exactly one counter row" or "one particular per ledger" should throw rather than continue, since a rollback costs a retry while a malformed receipt costs an accountant's trust. Explicit column lists on every INSERT (already the case **[L]**) keep new nullable vendor columns from breaking the adapter; a new NOT NULL column without default will make the insert fail, which is the safe outcome.
- **Upgrade detection.** Record a fingerprint (table and column names and types the adapter touches) at deploy, re-check it with an admin-side script before and after any ERP upgrade and in the periodic probe, and treat a mismatch as "lookups allowed, payments paused" for that school. Combined with the version handshake in question 5 this turns a silent vendor change into a visible, per-school switch-off.
- **Correlation.** Storing the order id and gateway reference on the ERP receipt (the adapter writes the gateway reference into `dd_no` **[L]**) is the cross-system correlation id the ACL guidance asks for; reconciliation between gateway, `pay_order` and ERP receipts can then be a single query per school.
- **Idempotency scope.** The order-row lock makes settlement idempotent per order; the per-student application lock plus the re-check of dues protects against two different orders for the same dues. Unlike Stripe's 24-hour key pruning, paid orders are kept indefinitely **[L]**, which is the correct choice for money records.

### Gaps
- The statement that Microsoft advises avoiding direct calls to eConnect procedures in favour of its API, and that GP patches can overwrite modified procedures, appeared only in search excerpts whose exact source pages I could not pin down; treat as unverified.
- The SAP Business One rule is reported from community threads citing Note 896891; the note's text was not read.
- No source was found on what Indian school ERP vendors' licence or support terms say about third-party writes, nor on how often such products change schema between versions; both are unknowns that affect how much upgrade-detection machinery is worth building.
- No public post-mortem of a payment integration corrupted by a vendor schema upgrade was found; the risk assessment rests on vendor guidance (SAP, Microsoft) rather than incident data.
