# Skip the ORM, keep one file per school

Keep the plain `mssql` driver and the stored procedures, accept **one hand-written SQL file per school** because every school's database is different, and roll the files out with **the small Node deploy script already in the repository** instead of an ORM or a packaged migration tool. To the owner's direct question: one Prisma per school is possible in principle, but with every database different it means one schema and one generated client per school, it cannot call the existing procedures properly, and it forces the web login to hold table rights, so it adds work without removing any. None of the seven ORMs and query builders examined can return the three result sets that `pay_get_dues` produces, and none shortens the per-school logic; they only move it from T-SQL into TypeScript. What keeps a file per school from becoming a mess is not a library but three fixed things the repository now has: an API that never changes per school, a school file with one agreed shape, and a deploy command that refuses a file breaking that shape. Of the three proportionate deployment options (a small custom runner, open-source Flyway, grate), the custom runner wins because it adds no runtime, reads the existing `schools.json`, and performs a contract check packaged tools do not supply; **Flyway's open-source edition is the best packaged tool** and the fallback if the script outgrows its present size. All of this rests on documentation, published source code and issue trackers, and on reading the repository on 10 November 2026; nothing was prototyped or run.

## One Prisma per school is possible, and worse on every count

Yes, it can be done. Prisma's own guide for several databases says "You give each database its own data contract, its own `prisma.config.ts`, and its own Prisma ORM client" ([Prisma docs](https://www.prisma.io/docs/guides/multiple-databases)). Applied here, where the owner has stated (10 November 2026) that every school's database is different, that means **one Prisma schema and one generated client per school**, each produced by pointing Prisma at a live copy of that school's database, plus application code that picks the right client for each school. The per-school work does not go away. What a school's SQL file does today (find the student, add up what is owed, write a receipt in that school's tables) would be written again per school, in TypeScript, against that school's generated model. The differences between schools would be recorded in a second language, not removed.

Four findings make it worse than the current design. Prisma has no way to call a stored procedure: the feature request has been open since December 2022, and its SQL Server adapter runs a raw `EXEC` and keeps only the first result set, so two of the three result sets from `pay_get_dues` would be lost ([prisma/orm #16776](https://github.com/prisma/orm/issues/16776), [adapter source](https://unpkg.com/@prisma/adapter-mssql@7.10.1/dist/index.js)). TypedSQL, Prisma's feature for typed raw SQL, covers MySQL and PostgreSQL but not SQL Server, and the request to add it has been open since September 2024 ([Prisma TypedSQL docs](https://www.prisma.io/docs/orm/prisma-client/using-raw-sql/typedsql), [prisma/orm #25215](https://github.com/prisma/orm/issues/25215)). **Prisma ORM 8, the release candidate that `npm install prisma` now installs, does not support SQL Server at all**; a SQL Server project must pin version 7, with no published date for parity ([Prisma docs](https://www.prisma.io/docs/orm/next)). And Prisma sends its SQL under the application's login, so the web login would need direct rights on each school's tables, which the next section shows is the largest cost. Two things were not verified: the exact per-database setup steps in Prisma 7 (the guide read was written for version 8), and the memory cost of holding dozens or hundreds of generated clients in one process.

## All seven ORMs would weaken the service without shrinking its SQL

The service's whole database surface is four stored-procedure calls in one 89-line file, `src/school-db.ts`, and one of those calls returns three result sets (student, dues, breakdown lines). The plain driver handles this natively: `request.execute()` exposes every result set in `result.recordsets`, plus output parameters and the return value ([mssql README](https://registry.npmjs.org/mssql)). None of the seven candidates does. Six have no stored-procedure feature at all, only a raw `EXEC` string, and then return either the first result set or all rows merged into one array. The seventh, MikroORM, has an experimental routine feature whose documentation says that on SQL Server "result sets emitted by a procedure are not surfaced" ([MikroORM docs](https://mikro-orm.io/docs/stored-routines)).

| Tool | SQL Server support, November 2026 | What happens to the three result sets |
|---|---|---|
| Plain `mssql` (today) | The driver itself | All three returned separately |
| Prisma | Version 7 only; version 8 release candidate has none | Raw `EXEC` only; first set only |
| Prisma TypedSQL | Not available for SQL Server | Not applicable |
| Drizzle | Only in the 1.0 release candidate | Raw `EXEC` only; first set only |
| Kysely 0.29 | Stable, built in | Raw `EXEC` only; rows merged into one array |
| Knex 3.3 | Stable | Raw `EXEC` only; rows merged into one array |
| TypeORM 1.1 | Stable | First set only; issue open since 2019 |
| Sequelize | Version 6 stable; version 7 still alpha | Merged into one array; issue open since 2017 |
| MikroORM 7 | Stable | Experimental routine feature; sets not surfaced |

The table comes from reading each tool's release pages, published driver source and issue tracker ([Drizzle releases](https://orm.drizzle.team/docs/latest-releases), [Drizzle source](https://unpkg.com/drizzle-orm@1.0.0-rc.5/node-mssql/session.js), [Kysely](https://unpkg.com/kysely@0.29.8/dist/dialect/mssql/mssql-driver.js), [Knex](https://unpkg.com/knex@3.3.0/lib/dialects/mssql/index.js), [TypeORM #5051](https://github.com/typeorm/typeorm/issues/5051), [Sequelize #8525](https://github.com/sequelize/sequelize/issues/8525), [sequelize.org](https://sequelize.org/v7/)); nothing was run against a live server.

The decisive cost is security. Microsoft describes the current design as a "security perimeter": revoke all permissions on tables, grant only EXECUTE on procedures, and callers reach data solely in the ways the procedures allow ([Microsoft Learn, archived 2017 page](https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server), [current ownership-chains tutorial](https://learn.microsoft.com/en-us/sql/relational-databases/tutorial-ownership-chains-and-context-switching)). All seven tools work by sending SQL composed in the application under the application's login, so using their table features means granting that login SELECT, INSERT and UPDATE on the school's ledger and receipt tables. **A leaked password could then read every student's finances or insert arbitrary receipts; today it can only run four procedures with their built-in checks**, a property the project's own test suite asserts. The protection depends on the procedures and the school's tables having the same owner in each database, which is worth confirming for every new school.

Nor would the SQL shrink. No ORM generates procedure bodies, so the joins, sums and window functions written against each school's tables would be rewritten in query-builder syntax, the receipt write would become several network round trips holding the school's receipt-counter lock instead of one call, and each school would need its own generated table model. Prisma's own guidance sends teams that "need full control over all database queries" to plain SQL drivers ([Prisma docs](https://www.prisma.io/docs/orm/overview/introduction/should-you-use-prisma)). The type safety an ORM is usually bought for already exists in the four hand-typed wrappers, and no maintained tool generates such wrappers from SQL Server procedures; the one direct match was last published in 2022 ([generator-mssql-types](https://registry.npmjs.org/generator-mssql-types)).

## A fixed contract, a template and a deploy check keep one file per school tidy

Per-customer code is exactly what integration guidance warns about: Microsoft lists "Specialized customizations for tenants" as a multi-tenant antipattern because it "adds complexity to your deployments and testing processes" ([Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/deployment-configuration)). Products whose customers share an external product avoid the problem with one adapter per product plus per-customer settings ([Airbyte Protocol](https://docs.airbyte.com/understanding-airbyte/airbyte-protocol), [Merge docs](https://docs.merge.dev/merge-unified/supplemental-data/field-mapping/overview)); that pattern would become relevant here only if two schools ever turn out to share a database layout. Where a customer's system is unique, such products fall back to what this project must do for every school: Flywire, which connects tuition payments to university ERPs and whose connectors all serve the same two functions (pulling balances, posting payments), offers a custom integration for home-grown systems ([Flywire developer docs](https://developers.flywire.com/education/Content/sfs-connectors.htm)). **The cost of a file per school cannot be removed, only contained**, and the containment the research supports is a small fixed contract, the smallest possible per-school part, and automated checks. The evidence is consistent but qualitative; no study of the cost was found.

The repository, as read later on 10 November 2026, is arranged that way:

```
schools-sql/common.sql      identical for every school: pay_order, pay_create_order, pay_settle, pay_fail_order,
                            pay_deployment and the role
schools-sql/<slug>.sql      one per school (today ranchi.sql): pay_get_dues and pay_mark_paid for that school's tables
schools-sql/_template.sql   the empty shape of a school file, copied to start a new school
tools/db.ts                 npm run db:deploy / db:status: installs, checks the contract, records the version
```

Three properties do the work. First, the application side never varies: `src/school-db.ts` calls the same four procedures for every school, so a new school adds no TypeScript, and the order lifecycle and settlement transaction live once in `common.sql`, leaving a school file only the translation. Microsoft calls this an anti-corruption layer, for "any external system that your development team doesn't control" ([Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer)). Second, the per-school part has one shape: two procedures with agreed inputs and outputs, started from `_template.sql`, with the school's constants declared as named variables (Ranchi's school code, for example) instead of scattered literals. Third, **the deploy checks the contract before keeping anything**. After running `common.sql` and the school's file in one transaction, `tools/db.ts` executes `pay_get_dues` for a non-existent admission number and verifies that three result sets come back with the agreed column names, compares the parameter list of `pay_mark_paid` with the contract, and rolls the whole deploy back if either check fails. It is the idea behind Airbyte's single acceptance suite that every connector must pass ([Airbyte](https://docs.airbyte.com/connector-development/testing-connectors/connector-acceptance-tests-reference)), applied at install time.

The check has limits worth knowing. It proves the shape of the answer, not its correctness: it compares column names but not types, it cannot tell whether the amounts are right, and it deliberately does not run `pay_mark_paid`, which writes receipts. The per-school tests and daily probe in the last section cover those gaps. Two rules from the research keep school files safe as they multiply. Use static SQL only, because dynamic SQL runs outside the ownership chain and the web login would then need direct table rights ([Sommarskog](https://www.sommarskog.se/grantperm.html)). And where the school's system already records a fact, read it instead of hard-coding it; Ranchi's file derives its ledger account codes from the ERP's own tables. One cost no structure removes: a change to the contract itself means editing every school file, so the contract should stay as small as it is. AI-assisted coding makes such files cheaper to write ([Julien Danjou](https://julien.danjou.info/blog/every-customer-gets-the-same-software/)), not cheaper to verify when they write money records into a live system.

## A 120-line Node runner is enough; Flyway is the fallback

Because every script uses `CREATE OR ALTER` and creates tables only when missing, the deployment tool has a narrow job: run the files against each school in order, stop on the first error, record in each database which version it holds, and report that across all schools. Three options do this proportionately. Flyway's "repeatable migrations" re-apply a file whenever its checksum changes and track it in a history table per database, accept `GO`-separated SQL Server scripts as they are, and come with an official multi-database tutorial built on a plain loop over targets ([Redgate docs, repeatable migrations](https://documentation.red-gate.com/fd/repeatable-migrations-273973335.html), [SQL Server](https://documentation.red-gate.com/flyway/reference/database-driver-reference/sql-server-database), [fleet rollout](https://documentation.red-gate.com/fd/tutorial-fleet-rollout-with-migrations-based-deployment-342852719.html)). grate treats views and stored procedures as scripts that "run when new or changed" and keeps its history in its own schema ([grate docs](https://grate-devs.github.io/grate/)). A custom runner on the `mssql` driver does the same in little more than 100 lines. No independent field comparison of the three was found.

The custom runner is the simplest of the three to live with. It needs no second runtime (Flyway is Java inside a Docker image, grate bundles .NET), it reads the school list the service already uses instead of a parallel configuration file, and it is written in the team's own language. It also exists. `tools/db.ts` (about 120 lines) installs each school in **one transaction, so a school is either fully on the new version or untouched**, records a SHA-256 fingerprint of `common.sql` plus the school's file in a `pay_deployment` table, and stops at the first failing school. `npm run db:status` then reports each school as up to date, out of date, changed in the database (one of our objects was modified after the last deploy) or never deployed. The contract check is the part a packaged tool would not supply: SQL Server's own metadata function describes only a procedure's first result set, so confirming all three takes a client that executes the procedure and inspects what comes back ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-describe-first-result-set-transact-sql)). Flyway lists advanced drift detection among its paid Enterprise extras ([Redgate editions](https://www.red-gate.com/products/flyway/editions/)).

The price is owning pitfalls a packaged tool hides. `GO` is not SQL: Microsoft documents it as a command understood only by sqlcmd and Management Studio, a procedure definition must sit alone in its batch, and even grate, a dedicated tool, shipped a fix for its `GO` splitting on 5 November 2026 ([Microsoft Learn, GO](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/sql-server-utilities-statements-go), [CREATE PROCEDURE](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-procedure-transact-sql), [grate releases](https://github.com/erikbra/grate/releases)). The existing script handles the main ones: it splits only on lines consisting of `GO`, sends each batch separately, rolls everything back on any error, and normalises line endings so the fingerprint is the same on Windows and macOS. **Two small gaps remain.** Nothing stops two deploys running against one school at the same moment; `sp_getapplock`, which Ranchi's file already uses per student, is the usual guard ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql)). And a repeat deploy re-applies everything instead of skipping a school already on the current fingerprint, which matters once "deploy all" means hundreds of databases. It also relies on a house rule: `GO` alone on its own line, never with a count, a trailing comment, or inside a comment block. This assessment comes from reading the file, not from running it.

The script should stay about this size. If it ever needs ordered one-time data migrations, parallel waves, or a second maintainer who expects a standard tool, the move is to **Flyway's open-source edition**, and it would cost little, because the SQL files stay as they are apart from a naming prefix; the contract check would have to be kept as a separate step. Flyway is preferred over grate for longevity (about 10,200 GitHub stars against grate's roughly 300) and for a smaller footprint in someone else's database (one history table against grate's schema of six) ([Flyway GitHub](https://github.com/flyway/flyway), [grate GitHub](https://github.com/erikbra/grate), [grate migration tables](https://grate-devs.github.io/grate/migration-tables/)). Use the `flyway/flyway` Docker image, not the Redgate-branded `redgate/flyway`: Redgate's editions page now describes its free Community edition as "for individuals and education", and the Teams edition no longer appears on it ([Flyway Docker docs](https://documentation.red-gate.com/fd/flyway-docker-321585710.html), [Redgate editions](https://www.red-gate.com/products/flyway/editions/)). Two points need a trial on the restored Ranchi backup before relying on it: whether the open-source edition covers every command in Redgate's fleet tutorial, and how Flyway behaves on first contact with a non-empty school database. Neither was confirmed from a primary source.

| Tool | Verdict | Deciding fact |
|---|---|---|
| Small Node runner on `mssql` | **Recommended now** | No new runtime, about 120 lines, already in the repository, checks the contract |
| Flyway, open-source edition | Best packaged tool; the fallback | Repeatable migrations, Apache-2.0, official multi-database tutorial |
| grate | Good fit, runner-up | MIT and plain SQL folders, but a small project whose 2.2.0 build bundles a release-candidate .NET runtime ([releases](https://github.com/erikbra/grate/releases)) |
| Liquibase | Workable, heavier | Needs a changelog describing every file; free edition no longer open source since version 5.0 (September 2025), though still free in production ([Liquibase](https://www.liquibase.com/blog/liquibase-community-for-the-future-fsl)) |
| DACPAC / sqlpackage | Overkill | Publishing requires `db_owner`; a whole-schema comparison engine for a database the team does not own ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/tools/sqlpackage/sqlpackage-publish)) |
| Atlas | Paid for this use | "The SQL Server driver is only available to Atlas users with the Pro Plan" ([Atlas](https://atlasgo.io/features)) |

## Version control, one-school-first and a daily probe matter more than the tool

First, put the project under version control. The working folder read for this report is not a Git repository, so the fingerprint stored in each school's `pay_deployment` table identifies a version nobody can retrieve or compare. Martin Fowler noted in 2003 that stored procedures are often not kept in version control at all ([martinfowler.com](https://martinfowler.com/articles/dblogic.html)); it is the one objection to database-side logic that costs nothing to remove.

Second, roll out to one school before all. Redgate's fleet guidance is to apply a change to one low-risk production target, watch it, then proceed in waves, and to keep a per-target status report afterwards ([Redgate docs](https://documentation.red-gate.com/fd/tutorial-fleet-rollout-with-migrations-based-deployment-342852719.html)). The existing commands support exactly that: `npm run db:deploy -- ranchi`, then `npm run db:deploy`, then `npm run db:status`. Deployment should use a dedicated login with rights to create procedures: never the service's own login, and not `sa` at a real school, which is what the development entry in `schools.json` uses today. Microsoft suggests how long a hand-edited `schools.json` will do: a hand-maintained tenant list becomes cumbersome "around 10 or more", and heavier machinery "needs to be justified by the number of tenants" ([Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/deployment-configuration)).

Third, let per-school tests and a daily probe cover what the deploy check cannot. The project's `test/pay.test.ts` already exercises lookup, the full payment flow and the permission boundary against a restored copy of Ranchi's database; each school needs the same treatment, plus a few known admission numbers with their expected dues, captured on a restored backup, so that any change to that school's file must reproduce them. Fowler's contract-test advice adds a second rhythm: checks against the live external system, run about daily ([martinfowler.com](https://martinfowler.com/bliki/ContractTest.html)). Here the thing that changes without notice is the school's own software, so **a read-only `pay_get_dues` call for a designated test student at each school each day** is worth more than any object-comparison tool.

Two further safeguards are design suggestions from the research, not documented industry practice. The service could read the deployed fingerprint at start-up and pause payments, though not lookups, for a school whose database is out of step; as read, nothing in `src/` consults `pay_deployment`. And an administrator-side check using SQL Server's `sys.dm_sql_referenced_entities`, which reports procedures that reference tables or columns that no longer exist, would catch a software upgrade at a school that broke its file before a parent does ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-sql-referenced-entities-transact-sql)). The largest unknown is commercial, not technical: whether each school's software vendor permits third-party procedures in its database, and whether its upgrades preserve them. Community threads report that SAP refuses support for Business One databases modified by outside SQL, though the SAP note they cite was not read ([SAP Community](https://answers.sap.com/questions/86313/how-to-update-oinm-table-value.html)). For every new school, the first question should be whether its system offers an API, import tables, or its own save-receipt procedure.

## Conclusion

The question arrived as a choice of library, and the owner's fact that every school is different settles it from the other side: the per-school logic is irreducible, so no tool can shrink it, and the only real choices are where it lives and what surrounds it. Kept in a stored procedure, it sits behind an EXECUTE-only login and one network call; moved into Prisma or any other ORM, it would be the same work with wider permissions. Because every script is plain, re-runnable SQL, the deployment tool is the least consequential decision here: moving from the Node script to Flyway or grate later means renaming files, not rewriting them.

What will decide whether this stays manageable at a hundred schools is something nobody has measured yet: how long a school file takes to write and to verify, and what each vendor allows. The second and third schools will answer more of that than any further tool evaluation, so treat those onboardings as the experiment: record the hours each file took, what the deploy check caught and what it missed, and what the vendor said. If two school files ever turn out nearly identical, that is the signal to revisit sharing.
